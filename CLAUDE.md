# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Plain CommonJS JavaScript: no build step, no linter. Yarn 4 is vendored (`.yarn/releases`, `.yarnrc.yml`). Node >= 24 (`package.json` engines): run `nvm use 24` first. System binaries: `ffmpeg` (media plugins) and `yt-dlp` (`youtube`, `insta`, `dl`; keep it recent, the Dockerfile installs the latest and `.update` runs `yt-dlp -U`).

```bash
yarn install            # no postinstall anymore
yarn test               # node --test --test-force-exit "test/**/*.test.js": ~4,900 tests, about a minute, no network, no WhatsApp
node --test --test-force-exit test/registry.test.js   # one test file (BOT_LANG=en for English; default fr)
OWB_NO_CONFIG_ENV=1 timeout 120 node --max-old-space-size=1024 --test --test-force-exit --test-timeout=30000 test/<file>.test.js   # the capped single-file run (agents, small machines): never two test processes at once, never the whole suite without `NODE_OPTIONS=--max-old-space-size=1024` and a `timeout`
node tools/check-unused-deps.js   # must print "0 unused dependencies"
yarn dev                # node index.js — prints a QR code and the admin panel setup link on first login
yarn start / yarn stop  # run under PM2 (ecosystem.config.js: 500M restart, --expose-gc)
yarn panel              # panel.js: same bot; with ADMIN_PANEL=false it keeps the legacy monitoring routes alone, for panel hosts
docker compose up -d    # Dockerfile runs `node --expose-gc index.js`; volumes for sessions/, db/, data/; /ping health check
node tools/admin-reset.js   # prints a single-use admin panel password reset link (bot may stay running)
node tools/merge-i18n.js / node tools/merge-panel-i18n.js   # merge translation fragments (see i18n)
node tools/measure-panel-memory.js   # RSS of the bot with and without the admin panel (modes `baseline`, `panel`) and with the messaging API off and on (`api-off`, `api-on`, idle); exits 0 when the panel delta is under 50 MB and the `api-on` minus `api-off` delta under 20 MiB (never reads config.env)
```

**Run every ad-hoc script, tool and agent command with `OWB_NO_CONFIG_ENV=1`**: `config.js` then skips `config.env` (the owner's secrets). `test/helpers/fakes.js#setupEnv` sets it for tests. Never read or print `config.env`, `sessions/`, `data/` or `database.db`.

`LOG_LEVEL=debug` shows plugin registration and command dispatch; `BAILEYS_LOG_LVL` controls Baileys' own logger (default `silent`). Configuration comes from `config.env` (copy `config.env.example`), loaded by `config.js` via dotenv, and from the admin panel; every setting is read through `config.js` (see "Settings"). Boolean flags are true only for the exact string `"true"`, except the opt-out ones (`ADMIN_PANEL`, `UPDATE_CHECK`, `DATABASE_SSL`, `ALERT_*`), which are false only for the exact string `"false"`. `BOT_LANG` defaults to `fr`. `yarn test` cannot cover buttons, anti-delete or welcome/goodbye on a real device: see the checklist in `docs/AUDIT_COMMANDES.md` section 7.

## Architecture

### Boot and client
`index.js` and `panel.js` are thin wrappers over `bootstrap({ mode: "normal" | "panel" })` in `lib/core/boot.js`, the single boot path: `logger.install()` and global error handlers → memory manager → `WhatsAppClient` + `BotRuntime` (`lib/core/botRuntime.js`: state, one in-process restart at a time, shutdown that never logs the device out) → HTTP server (`lib/admin/server.js`, started **before** the database so hosts see the port; a busy port is logged and never fatal) → `DATABASE.authenticate()` → `sync()` → `settingsStore.load()` → `languageManager.reload()` → `textOverrides.load()` → `apiState.load()` (the messaging API switch) → `PluginLoader.loadAll()` → `attachHandlers(client, runtime.handlerOptions)` → engines start (`stats`, `housekeeping`, `broadcaster`, `messaging`, `alerts`, `updater` checker) → `admin.start()` → `client.initialize()`. A change to boot order or collaborators goes in `boot.js` only (tests inject fakes through `options.deps`). `lib/baileys/client.js` wraps Baileys v7 (rc14; the 7.x line only exists as a prerelease), loaded with `require` then `import()` fallback; `mediaAdapter.js` hides download API differences. Auth is multi-file under `sessions/main/` (delete it, or use the panel's Pairing page, to re-pair); it reconnects after 3s unless logged out, pairs by QR or pairing code, restarts in-process through a generation token, and re-emits `messages` (notify batches only), `messages.update`, `groups.update`, `group-participants.update`, `ready`. Auto status view/react lives in the client.

### Pipeline (`lib/core/pipeline.js`, the only copy)
`processMessage` never throws; `attachHandlers` also wires `messages.update` (anti-delete), `group-participants.update` (`onGroupParticipants` hooks) and `ready` (`onReady` hooks). Per message:

1. `status@broadcast` → `statusSaver`, stop.
2. Wrap in `Message`, set `isCommand`, cache for anti-delete.
3. Disabled-chat gate (`BannedChat`): stop, except `unban` from an owner.
4. `viewOnceHandler` (never stops).
5. Quoted or interactive reply: a bare number quoting a message known to `buttonRegistry` becomes its button id; then each plugin's `handleButtonReply` (legacy `handleReply`) runs and the first truthy return consumes it (`apireplies.js`, priority 5, runs before every game and consumes the taps and quoted numbers of API messages). A prefixed command skips this step.
6. `onMessage` hooks, stop on truthy.
7. Sticker bound by `setcmd` → body becomes `PREFIX + command`.
8. Plain non-`fromMe` message → `autoResponderHandler` (not awaited), stop.
9. `registry.executeCommand`.

Each hook is isolated in try/catch. `handleMessage` drops new messages while `maintenanceMode` is active (backup restore) and `processMessage` brackets its work with `maintenanceMode.begin()`; after step 3, `stats.count("messages" | "group_msgs")`. **`sentIds` guard** (feature 004, the only change the messaging API made to the pipeline): right after the maintenance check `handleMessage` ignores the `fromMe` echo of a message this process sent for the API (`lib/messaging/sentIds.js`, filled by the outbox before `sendMessage`: 15 min, 2,000 ids), so it reaches neither the cache, the stats, a hook nor a command: an API text is never a command (`test/messaging-never-command.test.js`). Pipeline changes go in this file only.

### Plugins (`plugins/*.js`, `lib/plugins/`)
`loader.js` requires `plugins/*.js` in sorted order and registers modules exporting `command` + `execute` and/or hooks. Modules with neither (`buttons.js`, the empty `pollplus.js`) are skipped; `trackmessages.js`, `knownchats.js`, `groupguard.js` and `apireplies.js` are hook-only.

```js
module.exports = {
  command: { pattern: "name|alias", desc: getLang("plugins.x.desc"), type, fromMe, ownerOnly, onlyGroup, onlyPm, adminOnly,
             delegable, lockReason },           // delegable: can the panel open it to other people? lockReason only with delegable: false
  async execute(message, argsString, ctx) {},   // ctx = { command, rawArgs }; `this` is the plugin module
  async handleButtonReply(message) { return false }, // true only for your own ids
  async onMessage(message) {},                  // cheap and cached; truthy return consumes the message
  async onGroupParticipants(update, client) {}, // add/remove/promote/demote
  async onReady(client) {},                     // idempotent: runs on every (re)connection
  hookPriority: { onMessage: 20 },              // lower first, default 100, then load order
};
```

- Matching is exact: `pattern` is a `|` list of **literal** lower-case aliases in an alias map; the word after the prefix, lower-cased, must equal one (no regex). A duplicate alias logs a warning and the first registered keeps it.
- `executeCommand` checks in this order (feature 003; the banned-chat gate stays in the pipeline): the verdict of `commandPermissions.decide` (`owner` / `granted` / `closed` / `normal`); `closed` ends in silence (no reply, no reaction, no stats, no bus topic; one `info` log line per sender and command per minute); the `fromMe`/`ownerOnly` gate (synonyms; owner = `SUDO`, empty `SUDO` refuses everybody) unless the sender is `granted`; the command state (a command disabled in the panel, globally or in the group, answers `common.command_disabled`, owners and granted people included); `onlyGroup`, `onlyPm` (also for a granted person); `adminOnly` (group admin or owner) unless `granted`; then `execute`. With no rule the sequence is exactly the pre-003 one. Don't re-check these in the plugin; only `isBotAdmin()` before admin actions.
- **Command permissions** (feature 003; contracts in `specs/003-command-permissions/contracts/`). The panel lets the owner open a command to named people, everywhere or in one group: mode `extra` (normal level plus these people) or `only` (these people and the owners; everybody else is ignored in silence). Rules live in the `PermissionRule` table and are written **from the panel only** (no WhatsApp command). Only an entry with `delegable === true` is ever looked at: `registry.js` sets `delegable = typeof delegable === "boolean" ? delegable : !(fromMe || ownerOnly)`, so a future owner-only command is non-delegable unless its code says `delegable: true`, and `lockReason` (`code`, `update`, `data`, `lockout`, `config`; `null` unless `delegable: false`) is the reason the panel shows. 14 commands declare `delegable: false` (`exec`, `update`, `exportcontacts`, `ban`, `unban`, `setvv`, `getvv`, `antidelete`, `getantidelete`, `ar`, `statussave`, `setcmd`, `delcmd`, `getcmd`); `vv` and `save` declare `delegable: true` (still `fromMe: true`). `test/command-delegable.test.js` pins the 14 and fails when an owner-only plugin does not declare `delegable` itself. A delegated `.vv` never posts in the group: media, usage text and too-large notice go to the requester's DM (`plugins/vv.js`, best effort, never reads the `view_once` setting); a delegated `.save` is just as discreet (`plugins/save.js`: no reaction, media and texts go to the requester). `plugins/help.js` (`getVisibleCommands`, `findVisibleCommand`, both async) and `menu.js` / `buttonmenu.js` use the same `decide`: a `closed` command is absent from `.menu`/`.bmenu` and `.help <cmd>` answers like an unknown one, a `granted` one is shown.
- **What the rules do not cover**: `onMessage` hooks (`afk`, `addfilter`, `notify`, `trackmessages`, `groupguard`, `apireplies`) and `handleButtonReply` handlers (a click on an old interactive message is not gated); checks inside a plugin (`stats reset`, `idea`, `quote`, `reminder list all`, the cooldown exemptions of `chatgpt`, `gemini`, `imagen`, `voice`): a rule opens the command, not its owner-only sub-actions; `describeAccess` in `.help` (a granted member still reads "owner" on the `.vv` card) and `.help eval` from a non-owner (the card still shows; only `closed` hides); the `.role` states (`muted`, `banned`), which keep their own effect; the auto-vv (`viewOnceHandler`), unrelated to `.vv`.
- `argsString` is whitespace-collapsed: use `ctx.rawArgs` to keep newlines and `ctx.command` to know which alias matched.
- An exception from `execute` gives the user `common.error` (never `error.message`) and DMs the stack to the owners, at most once per command per 10 minutes (`cooldown.hit`); every error still reaches the log, the stats and the `command:error` bus topic.
- `onMessage` order: knownchats (5) → apireplies (6, consumes the poll votes of API messages) → role (10) → trackmessages (20) → afk (30) → notify (40) → groupguard (50, consumes when it deletes a message) → addfilter (90, consumes). Observers stay before consumers (`test/hooks.test.js` pins the order).
- `plugins/apireplies.js` (feature 004; hook-only, `hookPriority: { handleButtonReply: 5, onMessage: 6 }`) is a thin shell over `lib/messaging/replies.js`: it records what a person answered to an interactive API message (a tap on `api:reply:<waId>:<id>`, a bare number quoting it, a poll vote decrypted from `pollUpdateMessage`) in `ApiMessageResponse` and consumes it so no other feature reacts; with the switch off or after the reply window it still consumes a wire id but records nothing, and a plain text that merely looks like one is ignored.
- `plugins/groupguard.js` enforces the `Group` columns `antilink` and `antibot` (bot admin required; owners and group admins exempt; a command containing a link counts as a link; anti-bot removes only the message-id shapes no WhatsApp client produces, the 22-character `3EB0...` id is only logged). Mute has no hook: the panel's group service calls `groupSettingUpdate`.
- Button ids are `<plugin>:<action>[:<nonce>][:<arg>]`, never with JIDs (chat = `message.jid`). Send interactive messages through `plugins/buttons.js` (`sendQuickReplies`, `sendList`, `sendConfirm`, `sendPaginatedList`): it adds a numbered text fallback and records the ids in `lib/utils/buttonRegistry.js` (TTL 1 h) so a quoted number works. Clicks arrive as native-flow `paramsJson`; `Message` sets `body` to the id. The same file also exports the pure builders `buildQuickReplies` / `buildList` (`numbered: true` adds the numbered text the API always sends) and `sendPrepared(sock, jid, prepared, { messageId, quoted })` (one attempt, no fallback, no `buttonRegistry` record, throws), which the API's `buttons` and `list` formats use; `sendQuickReplies` and `sendList` call the builders and keep their fallback.

### `Message` and `lib/utils/`
Prefer `Message` helpers (`lib/classes/Message.js`) over the raw socket: `reply`, `react`, `send*`, `sendAudioFile` (sniffs type), `sendVoice` (ogg/opus), `getQuotedMedia({ maxBytes })` (null, or `{buffer,type,mimetype,fileLength}`; checks size before downloading), `getQuotedText()`, `quoted.key`, `isSudo`, `isBotAdmin`, `isSenderAdmin`, `kick/add/promote/demote`. `sender` is the phone-number JID when Baileys gives one, `senderLid` the LID; sudo and admin checks match both.
- `permissions.js`: `getOwnerJids`, `guardTarget(message, jid)` (refuses bot/owner/creator/self), `assertParticipantResult(res)` (`groupParticipantsUpdate` returns per-target `status`, success is `"200"`), `identitiesOf(message, jid, metadata)` (every PN/LID form of a person through the group participants and the LID mapping; exported for `commandPermissions.js`).
- `http.js`: `fetchJson`/`fetchBuffer` (30 s timeout, `MAX_UPLOAD` cap), `withTimeout`, `classifyError(err, { hasKey })` + `replyKeyFor(kind)` → `common.service_unavailable|not_configured|rate_limited`; `safeLog(err)` (never log an axios error: it holds API keys). Answer a missing key with `common.not_configured` before calling.
- `ffmpeg.js` (`runFfmpeg`, `toOpusVoice`; `execFile`, no shell), `media.js#withTempDir`, `downloader.js` (yt-dlp), `gameStore.js` (`createStore`: one game per chat, TTL, nonce), `cooldown.js` (`hit(user, key, ms)` → remaining ms), `scheduler.js` (persisted reminders, one 20 s loop started by `reminder.onReady`).
- `settingsCache.js`: `getOrLoad(key, loader, ttl)`, 5-minute TTL; keys `view_once`, `anti_delete`, `auto_responder`, `banned_chats`, `sticker_cmds`, `afk_users`, `command_state`, `command_perms`, `api_keys` (the API keys by lookup id, including revoked ones), `filters:<jid>`, `group:<jid>`, `roles:<jid>`. **A setter that writes a cached setting must call `settingsCache.invalidate(key)`** (the panel's services go through the same setters as the commands).
- `schema.js`: the strict schema core shared by the panel (`lib/admin/http/request.js` wraps it and rethrows a `SchemaError` as `AdminError`) and the public API: `check`, `validate`, `SchemaError`, `codePoints`; nested `shape` and `unique` arrays, dotted error paths (`buttons.1.id`), `<path>.$unknown` for an unknown property (neither its name nor a value is echoed). Never requires `lib/admin/**`.
- `sendGate.js`: the process-wide pacing floor (`createSendGate`, `shared`): `ready(at)`, `reserve(at)`, `seed(ms)`, `waitMs`; the messaging outbox and the `broadcaster` share the one instance, so no two automatic sends are closer than `max(2000, SEND_MIN_SPACING_MS)` plus a 0 to 20 % jitter.
- `apiState.js`: the messaging API switch and its plain-HTTP network list (the singleton `ApiState` row, `id: 1`): `load`, `isEnabled()` (`enabled && ADMIN_PANEL !== false`), `get`, `setEnabled`, `setPlainHttpFrom` (private ranges only, 20 entries), `setState`, `onChange`. A read never creates the row; **it is not a settings-catalog entry** (see Settings).
- `stickerMaker.js`: `imageToWebp`, `buildExif`, `withStickerExif` and their constants, moved out of `plugins/sticker.js` (the plugin and the API's `sticker` format share them; `sharp` and `node-webpmux` stay required inside the functions).
- `warnings.js`: the shared helper over the `Warn` rows (`.warn`, `groupguard`, the panel's Groups page): atomic increment, VIP exemption, placeholders. Don't reimplement it.
- `logger.js`: **the only logger factory**, `createLogger(name)`; one root pino with the secret redactor and a 1000-entry log ring (what the panel's Logs page shows), `printToConsole` for text that must reach the real stdout (setup link, QR), `install()` captures `console.*`. No `pino(` anywhere else except the two Baileys calls of `lib/baileys/client.js` (`test/admin-logging.test.js` fails on it); no `console.*` in `lib/admin/**`.
- `events.js`: the core bus, three topics only (`command:error`, `key:refused`, `groupguard:action`), `emitSafe(topic, payload)` isolates listeners. It exists to avoid require cycles (`http.js` → `alerts.js`); don't add topics casually.
- Engines (run whether or not the panel is enabled; start-up in `boot.js`): `stats.js` (daily counters), `housekeeping.js` (daily retention and `data/tmp` sweep), `broadcaster.js` + `recurrence.js` (one-time and recurring broadcasts, at most once per target), `messaging` (`lib/messaging/index.js`, the messaging API's outbox, started between `broadcaster` and `alerts`; see "Messaging API"), `alerts.js` (owner WhatsApp alerts, rate limits, queue during disconnections), `updater.js` + `ytdlpUpdate.js` (self-update: fast-forward, smoke boot via `tools/verify-boot.js`, rollback; `plugins/update.js` and the panel share it), `runtime.js` (container / supervisor detection, automatic bind address), `maintenanceMode.js`, `commandState.js`, `commandPermissions.js` (read side of the command permissions: `decide(entry, message, { isOwner })` → frozen `{ verdict, scope, mode }`, never throws, fails open to `normal`; no write function, the panel service writes and calls `invalidate()`; requires only `../database`, `./settingsCache`, `./permissions`, `./logger`, never the registry), `textOverrides.js`, `knownChats.js`, `mutex.js` (`withLock`: in-memory SQLite has one connection, so multi-statement writes are serialized), `safeFs.js`. Engines take `now` in their options, create no timer at `require` time, `unref()` their timers, and never require `lib/admin/**` (only the three log leaves `lib/admin/logs/*` are allowed).

### Settings (`config.js`, `lib/utils/settingsCatalog.js`, `settingsStore.js`, `secretBox.js`)
`config.js` exports the same object as before, but each setting is an accessor over `settingsStore`: runtime assignment (tests only) → **panel override** (`SettingOverride` row) → environment / `config.env` → code default. `lib/utils/settingsCatalog.js` is the single source (pure data, 112 entries: env name, type, validation, default, theme, `effect` immediate / restart / boot-only, `secret`, `testService`, `adapter`). A new setting is a catalog entry **plus** a line in `config.env.example` (`test/settings-example.test.js`), `settings.<KEY>.label` and `.desc` in the panel catalogs, and a reader that uses `config.KEY`. Settings whose truth already lives in a model or file (anti-delete, view-once, auto responder, the status-save list) are catalog entries with an `adapter` calling the same code as the commands. **The one exception is the messaging API switch**: its truth is the `ApiState` row behind `lib/utils/apiState.js`, deliberately not a catalog entry, so no setting, environment variable or backup can turn the API on. The 11 settings of feature 004 are panel-only (`env: null`, so no `config.env.example` line): `SEND_MIN_SPACING_MS` (up only, floor 2000), `API_RATE_PER_MINUTE`, `API_RATE_PER_DAY`, `API_MAX_PENDING`, `API_QUEUE_MAX`, `API_QUEUE_EXPIRY_MIN`, `API_RETENTION_DAYS`, `API_REPLY_WINDOW_DAYS` (a cross validator keeps it at most the retention) and the alert toggles `ALERT_API_ORIGIN_BLOCKED`, `ALERT_API_KEY_NEW_IP` (**false** by default) and `ALERT_API_PAUSED`; 78 entries are editable and 34 read-only. Secrets set in the panel are stored as `enc:v1:` (AES-256-GCM, key in `data/panel.key`) and registered with the log redactor. Boot-only settings (`ADMIN_PANEL`, `PANEL_*`, `DATABASE_*`, `YTDLP_PATH`, `LOG_FORMAT`...) and the 21 settings no code reads ("inactive") are shown read-only.

**Capture-site rule**: never copy a `config.X` into a module-level constant, a class field or a default parameter (it would ignore later overrides). Read it at call time; a timer built from settings exposes `reconfigure()` (`conversationManager`, `antiDeleteHandler`, `memoryManager`); a cached credential or client is dropped on `settingsStore.onChange([...])`. `test/capture-sites.test.js` pins the known sites; `lib/api/**`, `lib/messaging/**` and `apiState.js` have no top-level `= config.`, and a changed quota, spacing, expiry or reply window applies to the next request or message, never to rows already queued (a value copied into a row, such as `expiresAt` or `repliesUntil`, is a snapshot).

### Admin panel (`lib/admin/`, feature 002; contracts in `specs/002-admin-panel/contracts/`)
On by default (`ADMIN_PANEL`), part of the bot process, in both launchers. Layout: `http/` (raw `node:http` router, security, SSE, uploads, trust proxy), `auth/` (scrypt password, sessions, one-time tokens, throttling), `routes/<area>.js`, `services/<area>.js`, `backup/`, `logs/` (redactor, ring, console capture: the only `lib/admin` files the engines may require), `monitoring.js` (the legacy public routes, moved verbatim), `server.js`, `public/` (the SPA).
- **Every route declares `auth`** (`"session"` or `"public"`; registering without it throws at boot), plus `csrf`, `touch`, `bodyLimit`/`upload` where needed, and `stepUp` (`true` or `"conditional"`, unsafe `session` routes only; see the API area). Validation is a strict schema that builds a fresh object (an unknown property is `422 validation_failed`). A handler returns codes and parameters of the error envelope, never prose, and audits through `ctx.audit(...)`; a destructive route requires the server-side `confirm`. `test/admin-security.test.js` enumerates the route table (no route without a session, no change from another site).
- A route module exports `register({ router, deps, hub, jobs, audit, onStart, onStop })`; `routes/index.js` loads every file in sorted order, so a new area is one new file. Resolve engines lazily (`deps.x || require("../../utils/x")` inside `register()` or the handler) so a test can inject a fake. A service is a factory `create<Area>Service(deps)` that never touches `req`/`res`.
- **Permissions area** (feature 003; `specs/003-command-permissions/contracts/admin-permissions-api.md`): `routes/permissions.js` + `services/permissions.js` (`createPermissionsService`) serve PERM-1..7 (`GET /admin/api/permissions`, `GET|PUT|DELETE /admin/api/commands/:name/permissions[/everywhere]`, `GET /admin/api/groups/:jid/permissions`, `PUT|DELETE /admin/api/groups/:jid/permissions/:name`; the literal segment `everywhere` is the scope `*`, which is not valid in a path). A PUT is a full replace of one `(command, scope)` row under `mutex.withLock("permissions")`, calls `commandPermissions.invalidate()` after the write and audits once, only when something changed: `command.permission.set` / `command.permission.delete` (target `<command>:<scope>`, detail `{ mode, previousMode, added, removed }` with compact ids). A non-delegable command is refused (`422 fields.name = not_allowed`), the DELETE routes are single-rule, idempotent and take no `confirm`, and the people are `{ pn, lid }` (typed numbers need the country code; membership is not checked). GRP-3 `counts.permissions`, GRP-6 `deleted.permissionRules` (forgetting a left group deletes its rules) and the internal `groups.participants(jid)` belong to this area; `test/admin-integration.test.js#contractRoutes()` also parses the 003 API contract. UI: the group page "Permissions" tab (`groups-permissions.mjs`) and, on the Commands page, a Permissions column, the "everywhere" card (`commands-permissions.mjs`) and the orphan rows; the shared logic and editor are `permissions-logic.mjs`, `permissions-editor.mjs`, `permissions-members.mjs`, `permissions-picker.mjs`.
- **API area** (feature 004; `specs/004-messaging-api/contracts/admin-api.md` and `panel-ui.md`): `routes/api.js` + `services/api.js` (`createApiService`) serve API-1..13 under `/admin/api/api` (state and switch, catalog of rights/formats/endpoints, keys list/create/update/duplicate/revoke, message history and detail, the test send API-11 through the same engine with `source: "panel"`, usage, OpenAPI download), plus AUTH-7 `POST /admin/api/session/reauth` in `routes/auth.js`. **Step-up**: the router option `stepUp: true | "conditional"` asks for the administrator password again before a change that widens access. `true` asks after validation (API-5, API-7); `"conditional"` gives the handler `ctx.stepUp(reasons)`, called **last** and only when the diff against the stored row widens (API-2, API-6; the exact predicate is `services/api.js#widenings`, mirrored by the SPA and pinned by `test/fixtures/api-widenings.json`). The gate is `auth.requireRecent(session, now)` over `confirmedAt` on the session cache entry: a fixed 5-minute window (`sessions.STEP_UP_MS`) started by a login or AUTH-7, per session, lost on a restart, and a missing gate fails closed (`403 password_required`). `admin.routes()` rows carry a `stepUp` column that `test/admin-security.test.js` pins. A key is created with its whole token returned once (`{ key, secret }`) and never again; updates use an optimistic `version`; revoke needs `confirm` and cancels the key's queued messages; the `anyone` recipient mode needs `confirm: ["policy_anyone"]`. Upload purpose `api` (`PUT /admin/api/uploads?purpose=api`) feeds the test form. Audit actions `api.enable`, `api.disable`, `api.plainhttp.update`, `api.key.create|duplicate|update|revoke`, `api.test`, `api.origin.block` and `account.confirm`: no secret, recipient or message text in a row. SPA: `views/api.mjs` (tabs Keys, History, Usage, Test, Docs) over `views/api-*.mjs`, pure logic in `api-logic.mjs` and `api-form-logic.mjs`, the test form and the Docs built from the registry's format descriptors (a new format needs no SPA edit), `reauth.mjs` + `components/reauth-dialog.mjs` mounted in `app.mjs`.
- The SPA is native ES modules (`.mjs`) with vendored Preact + htm and no build step. Browser code uses no `innerHTML`/`eval`/inline script or style/third-party URL (strict CSP; `test/admin-frontend.test.js`). A view is `public/js/views/<area>.mjs` with its pure logic in `<area>-logic.mjs` (importable by `node:test`).
- The legacy endpoints (`/health`, `/healthz`, `/status`, `/ping`, `/metrics`, `/api/info`, `POST /api/restart`) are frozen by `test/panel.test.js` and `test/panel-legacy.test.js`. Bind address: `127.0.0.1` locally, `0.0.0.0` in a container or when the host sets `PORT`, `PANEL_HOST` wins (`lib/utils/runtime.js`).

### Messaging API (`lib/messaging/`, `lib/api/`, feature 004; contracts in `specs/004-messaging-api/contracts/`, user guide `docs/API.md`)
Off by default and present only while the panel is (`ADMIN_PANEL`); served by the panel's HTTP server on the same port. Four endpoints under `/api/v1` authenticated by a key (`Authorization: Bearer owbk_<16 hex>_<43 base64url>`, never the panel session): `POST /messages` (13 formats, JSON or multipart, `wait`, `Idempotency-Key`), `GET /messages/:id`, `GET /messages`, `GET /openapi.json`. The four tables `ApiKey`, `ApiMessage`, `ApiMessageResponse`, `ApiState` are never exported by a backup.
- **Engine `lib/messaging/`** never requires `lib/api/**` or `lib/admin/**` (single exception: `apiState.setPlainHttpFrom` lazily requires the leaf `lib/api/ipRules.js`). `index.js` is the facade and the `messaging` entry of `boot.js` `ENGINES`: `start(client)` always loads the format registry and runs `outbox.recover()` (a crash never leaves rows `queued` or `sending`, even with `ADMIN_PANEL=false`) and only while `apiState.isEnabled()` arms the 1 s tick timer and the receipts listener; its `apiState.onChange` subscription is the only listener a disabled API holds, and `disable()` cancels every `queued` row. `submit`, `get`, `list`, `waitFor`, `describeResponses`, `cancelForKey`, `sweepMedia` are what the API pipeline, the panel service and `housekeeping` call. `outbox.js`: a row of `api_messages` **is** the queue; every transition is one conditional `UPDATE ... WHERE status = :from` (a lost race is ignored) and the claim to `sending` precedes the single send, so a crash leaves `unknown` and never a second send (at-most-once); pacing goes through `sendGate`, a message not sent within `API_QUEUE_EXPIRY_MIN` is `expired`, and three negative acks `463` within 10 minutes pause the queue 15 minutes (`api_paused` alert). `formats/*.js`: one self-describing module per format (`fields` schema, `build`, `prepare`, `refine`, `normalize`, descriptor) behind the registry `formats/index.js` (rights `messages.send.<name>`, descriptors for the panel): a new format is one new file, its tests and its panel texts (`api.format.<name>.label|desc|field.<path>.label|hint`). Also `recipients.js` (parse, policy `list|known|anyone`, the bot's own number, disabled chats, reachability), `sniff.js` and `stage.js` (content judged by its bytes; media under `data/api-media/<publicId>/`), `urlFetch.js` (the SSRF-safe fetcher and the only network caller: https, port 443, DNS names only, every resolved address public, redirects revalidated), `replies.js`, `receipts.js`, `sentIds.js`, `vcard.js`, `errors.js` (`MessagingError`, `MESSAGING_STATUS`), `limits.js`. **An API text is never a command**: nothing in `lib/messaging/**` reads `config.PREFIX`, and the pipeline's `sentIds` guard drops the echo.
- **HTTP layer `lib/api/`** may require from the panel only `lib/admin/http/*`, `lib/admin/auth/rateLimit.js` and `lib/admin/logs/redactor.js`. `createApi(deps)` (`index.js`) is built by `createAdmin` and `createPanelServer` tries `api.handle(req, res)` before `admin.handle`; `handle` returns false, so the legacy handler answers exactly as for any unknown URL, when the switch is off or the endpoint registry failed. `pipeline.js#dispatch` runs the ordered steps of `public-api.md` section 5 (gate, verb, transport, browser, key in URL, origin block, authenticate, key state, IP, route, rights, body, recipient, quotas, validation, media, engine): **the order is a security property**, change it in this file only and keep `test/api-pipeline.test.js` and `test/api-security.test.js` green. `registry.js#loadEndpoints` requires `endpoints/*.js` (one module each) and **denies by default**: an endpoint without a right makes the whole API unserved, there is no public endpoint. Others: `router.js` (its own table, literal paths), `keyStore.js` (SHA-256 of the secret only, constant-time compare, cache key `api_keys`, write-behind of the usage columns), `transport.js` (HTTPS rule, `plainHttpFrom`), `limits.js` (minute window and local-day counters rebuilt from `api_messages`), `idempotency.js` (24 h, keyed HMAC fingerprint), `multipart.js` + `upload.js` (hand-written parser, no dependency), `present.js` (explicit field lists, never `row.get()` or `toJSON()`), `openapi.js` (pure builder over the registries), `errors.js` (`API_STATUS`, disjoint from `MESSAGING_STATUS`), `ipRules.js`, `version.js` (`API_VERSION`).
- Registries drive the rest: a module added to `lib/api/endpoints/` or `lib/messaging/formats/` appears by itself in the rights catalogue, the OpenAPI document, the panel's Keys, Test and Docs and `test/api-contract.test.js`. Logs and audit never hold a key, a token fragment, a message text, a file name, an URL or a recipient in clear (`mask(jid)`, `publicId`, the key's integer id and name; `safeLog(err)`); `test/api-leak-scan.test.js` and `test/admin-api-leak.test.js` scan for it. No `console.*` and no `pino(` in `lib/api/**` or `lib/messaging/**`. Housekeeping adds five daily steps (idempotency, transient content, messages and responses, revoked keys, media) with the retention `API_RETENTION_DAYS`, with or without the panel.

### Database (`lib/database/`)
Sequelize: Postgres when `DATABASE_URL` contains `postgres` (SSL unless `DATABASE_SSL=false`), else SQLite at `DATABASE_URL` or `./database.db` (`:memory:` in tests). Each file in `models/` exports `(sequelize) => Model` and is auto-loaded under its filename. `sync()` is **additive**, not `alter: true` (which turned composite keys into per-column UNIQUE on SQLite): it creates missing tables and indexes, adds missing nullable/defaulted columns, and repairs SQLite tables damaged by the old `alter`. It never alters or drops a column, and a new unique index on an existing table is not allowed; a column change needs a hand-written migration. The Postgres path is untested. The admin panel added 14 tables (`AdminAccount`, `AdminSession`, `AdminToken`, `AuditLog`, `SettingOverride`, `TextOverride`, `CommandState`, `KnownChat`, `DailyStat`, `Broadcast`, `BroadcastRun`, `BroadcastTarget`, `AlertState`, `AlertOutbox`) and altered none, so the additive `sync()` holds: they appear on the next start, a new column on one of them must be nullable or defaulted, and a unique index on an existing table is still forbidden. A new model must also be listed in `MODELS` (exported) or `EXCLUDED_MODELS` (never exported) of `lib/admin/backup/format.js`. Feature 003 added one table, `PermissionRule` (`permission_rules`, PK `(command, scope)`, `mode` `extra`|`only`, `people` JSON `[{ pn, lid }]` of at most 100; the model repeats the engine's literals because it cannot require it, a test pins them), and altered none; `MODELS` now exports 26 models, and a restore validates each rule through the model. The engine reads the whole table through the `command_perms` cache key (never with `raw: true`: a JSON column comes back as a string on SQLite). Feature 004 added four tables, `ApiKey` (`api_keys`), `ApiMessage` (`api_messages`, which is also the send queue), `ApiMessageResponse` (`api_message_responses`) and `ApiState` (`api_state`, a singleton), additive again and all four in `EXCLUDED_MODELS` (now 11 entries; `MODELS` stays 26), so a backup never exports them and a restore never touches, revives or enables anything of them. Their JSON columns (`rights`, `recipients`, `ipAllow`, `seenIps`, `choices`, `choiceIds`, `plainHttpFrom`) are read through model instances, never `raw: true`; the unique indexes are in `indexes` (no per-column `UNIQUE`, NULLs are distinct in them); `ApiKey.nameKey` is NULL once the key is revoked so a name is reusable. Message content lives in `ApiMessage.payload` only until the status is final, then it is erased in the same write. Economy updates are atomic (`UPDATE ... WHERE balance >= :n`, transactions); stats use `increment`.

### i18n (`lib/utils/language.js`, `lang/*.json`)
Every user-facing string goes through `getLang("plugins.<name>.<key>", ...args)` (`{0}`, `{1}`); shared text lives under `common.*`. Never `getLang(k) || "fallback"` (a missing key returns the key). `en` and `fr` must have the **same keys**; other locales fall back to `en`. `command.desc` is evaluated at require time. Add keys in a fragment `specs/001-audit-fix-commands/i18n/<plugin>.json` (`{ "en": { "plugins.x.k": "…" }, "fr": {…} }`, flat dot keys) then run `node tools/merge-i18n.js` (`--dry-run` first), or edit both `lang/en.json` and `lang/fr.json`. Feature 002 uses two fragment families in `specs/002-admin-panel/i18n/`: `bot-<area>.json` (bot texts: replies, alerts, console lines; merged into `lang/*.json` with `node tools/merge-i18n.js --frag-dir specs/002-admin-panel/i18n --pattern "bot-*.json"`) and `panel-<area>.json` (panel UI strings, `t("area.key")` in `lib/admin/public/js/**`; merged into the flat `lib/admin/public/i18n/{en,fr}.json` with `node tools/merge-panel-i18n.js`). Feature 003 adds no bot key (a silent refusal has no text; a delegated `.vv` reuses `plugins.vv.usage`, `common.media_too_large`, `plugins.viewonce.forwarded`) and one panel fragment, `specs/003-command-permissions/i18n/panel-permissions.json`, merged with `node tools/merge-panel-i18n.js --frag-dir specs/003-command-permissions/i18n` (`test/admin-i18n.test.js` scans both fragment directories). Feature 004 adds `specs/004-messaging-api/i18n/`: `bot-api.json` (the three `alerts.api_*` texts and `api.registry_failed`; `node tools/merge-i18n.js --frag-dir specs/004-messaging-api/i18n --pattern "bot-*.json"`), `panel-api.json` and `panel-api-server.json` (`node tools/merge-panel-i18n.js --frag-dir specs/004-messaging-api/i18n`; `panel-api.json` has registry-driven keys `api.format.<name>...` that follow the formats, and the six `alerts.type_api_*` titles sit in the 002 fragment `panel-alerts.json`). `test/admin-i18n.test.js` scans every fragment directory. The public API and its OpenAPI document are English only; `docs/API.md` is the French guide. Once merged, the catalogs are the source: edit them directly or add a new fragment. The HTTP API sends codes and parameters, never prose; `test/admin-i18n.test.js` checks the panel catalogs. `test/i18n.test.js` fails on a missing key or a literal text passed to `reply()`/`sendMessage`; a deliberate exception takes `// i18n-ignore` on the same or previous line.
