**Input**: Design documents from `specs/002-admin-panel/`

**Organization**: tasks are grouped by user story, but the unit of parallel work is the **agent**, and every file has exactly ONE owner agent per wave (W0 foundation, W1 areas, W2 integration). File sets are disjoint inside a wave, so agents run in parallel. A story phase says which story a task serves, not when it runs: **an agent runs its own tasks in ID order, even when they sit in different phases** (for example W-DASH does the US2 tasks of Phase 4, then the US7 tasks of Phase 9). The agent index in "Dependencies & Execution Order" gives each agent's task list.

## Format: `- [ ] T### [P?] [USn?] Description — agent X (sonnet)`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task)
- **[USn]**: user story US1 to US13 from spec.md (omitted on pure infrastructure)
- **Agent / model**: each task ends with `— agent X (sonnet)`. Per the user's routing rule every agent is `sonnet` (Sonnet 5.5 subagent); Opus is planned for nothing and is used only if a core W0 piece (F2, F5, F8) fails review twice. `main` is the orchestrating session. Agent ids: F1 to F8 (W0), W-DASH, W-SET, W-PAIR, W-CMD, W-GRP, W-DATA, W-BC, W-BAK, W-MNT, W-ALR (W1), W2-A, W2-B, W2-C, Z (W2).
- Cites such as "per contracts/runtime.md §5" or "routes SET-1..SET-3 of contracts/admin-http-api.md" name the exact contract section to read. Quoted text in a model task is verbatim from [data-model.md](data-model.md).
- Every checkbox below is open (`- [ ]`): nothing of feature 002 is implemented yet.

## Rules for every implementation agent (include in each agent prompt)

1. **Read first**: `CLAUDE.md`, the contract sections cited by your tasks ([contracts/runtime.md](contracts/runtime.md), [contracts/admin-http-api.md](contracts/admin-http-api.md), [contracts/settings-catalog.md](contracts/settings-catalog.md), [data-model.md](data-model.md)), and the research decisions U1-U19, O1-O2, R1-R5, C1 in [research.md](research.md). Where `research/*.md` disagrees with `research.md` or a contract, the latter wins. Where `contracts/runtime.md` and `contracts/admin-http-api.md` disagree, the API contract wins for anything HTTP-visible (for example CORS on the legacy `/api/restart`, task `T051`).
2. **Edit only the files listed in your tasks.** Never edit a file owned by another agent in the same wave; list the need under "Requests" in your final report. Never edit `lang/*.json`, `lib/admin/public/i18n/*.json`, `package.json` or `yarn.lock` (exceptions in the shared-files table). No new npm dependency: the vendored preact/htm files are files, not dependencies.
3. **Never read or print** `config.env`, `sessions/`, `data/`, `database.db` or any secret. Tests use `DATABASE_URL=":memory:"`, `fs.mkdtemp` directories, inline environment variables, fake clocks and stubs; nothing touches the real `data/`, `sessions/` or `database.db`, and nothing needs the network.
4. **No commits.** The orchestrator commits after each agent (French conventional commits, one per finished agent). Do not run `git stash`, `git reset`, `git checkout` or anything that rewrites the working tree of other agents.
5. **Runtime**: `export PATH=$HOME/.nvm/versions/node/v24.20.0/bin:$PATH` before any command. Yarn is vendored: `node .yarn/releases/yarn-4.17.0.cjs <command>`. Use the agent's scratchpad directory for temporary files, never the repository.
6. **Before finishing**: `node --check <file>` on every edited `.js` and `.mjs` file; run your own test files with `node --test --test-force-exit test/<file>.test.js`; run the whole suite (`node .yarn/releases/yarn-4.17.0.cjs test`, with `BOT_LANG=fr` and `BOT_LANG=en` once). A failure in a file you do not own is reported as a Request, never fixed in place.
7. **Style**: match the surrounding code. CommonJS (`.js`) everywhere except `lib/admin/public/**` (native ES modules, `.mjs`); the existing quote style of each edited file (double quotes in new files); 2 spaces; comment density like the neighbours. Browser code: no `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`, no `eval`/`new Function`, no inline `<script>` or `style=`, no URL to a third-party host (strict CSP, FR-010).
8. **i18n**. Bot texts (anything sent on WhatsApp or printed to the console by the bot: replies, alerts, `common.command_disabled`, the setup-link line, boot warnings) go through `getLang("<area>.<key>", ...args)`, with the keys written to `specs/002-admin-panel/i18n/bot-<area>.json` (`{ "en": { "area.key": "…" }, "fr": { … } }`, flat dot keys, identical key sets, natural French with accents). Panel UI strings (`t("<area>.<key>")` in `lib/admin/public/js/**`) go to `specs/002-admin-panel/i18n/panel-<area>.json`, same shape. W2-A merges both families. Never write `getLang(k) || "fallback"`; a literal text passed to `reply()`/`sendMessage` fails `test/i18n.test.js` (`// i18n-ignore` only for a deliberate exception). The HTTP API sends codes and parameters, never prose.
9. **Secrets and logs**: a secret never appears in a response, a log line, an audit detail, an error body or a test snapshot; use `safeLog(err)` from `lib/utils/http.js` (never log an axios error); no `console.*` in `lib/admin/**` (use `createLogger` from `lib/utils/logger.js`, and `printToConsole` for the setup link); never log request bodies, headers or query strings.
10. **Every route declares `auth`** (and `csrf`, `touch`, `db: "optional"` where the route tables of admin-http-api.md §2 say so). Validation is a strict schema that builds a fresh object (an unknown property gives `422 validation_failed` with `fields.$unknown`). A handler returns codes and parameters of the error envelope (§1.9), never prose. A destructive route carries the server-side `confirm` of §1.10 where that section lists it. Audit with the vocabulary of §1.15, through `ctx.audit(...)`.
11. **Time and timers**: anything that depends on the clock takes `now` in its options (default `Date.now()`); no timer at `require` time; `start()` is idempotent, timers are `unref()`'d, `stop()` clears them (contracts/runtime.md §0).
12. **Engines vs panel**: code in `lib/utils/**`, `lib/core/**`, `lib/plugins/**` and `plugins/**` never requires `lib/admin/**` (the three log leaves excepted, runtime.md §0). Route modules resolve their engines lazily as `deps.X || require("../../utils/X")` inside `register()` or the handler, never at module top level, so a test can inject a fake and a module delivered by a later batch does not break the loading of the others.
13. **Admin module conventions** (defined by F4/F6 in W0, used by every W1 agent): a route module `lib/admin/routes/<area>.js` exports `register({ router, deps, hub, jobs, audit, onStart, onStop })`, called once by the auto-loader (sorted order; nobody edits a shared index); a service `lib/admin/services/<area>.js` exports a factory `create<Area>Service(deps)` and never touches `req`/`res`; a view `lib/admin/public/js/views/<area>.mjs` default-exports a Preact component (htm templates), may add `js/views/<area>-*.mjs` and `js/components/<area>-*.mjs` files, and keeps pure logic (form diffing, validation, pre-fill builders) in `js/views/<area>-logic.mjs` with no DOM access at import time so `node:test` can import it. A view that lacks a shared component files a Request for W2-A instead of editing `js/components/*`.
14. **Tests**: new helper files go in new files under `test/helpers/` that you own; `test/helpers/fakes.js` is not edited in W1. Fixtures are literal and small. Time-dependent behaviour uses `test/helpers/fakeClock.js` (F4) or `mock.timers`.
15. **Final report**: for each owned file the status, the tests added and their result (including the full-suite result), contract deviations with the reason, the list of i18n fragment files with their key counts, and the "Requests" for files owned by others. The orchestrator feeds the Requests into the next wave.

## Phase 2: Foundational (W0, blocking prerequisites)

**Purpose**: the engines, the HTTP core, the authentication, the data model, the client lifecycle and the SPA shell that every story needs. Eight agents with disjoint file sets.

**⚠️ CRITICAL**: no W1 task may start before the W0 checkpoint.

**Stages** (a practical cap of about 5 concurrent agents applies):

- **Stage A** (start together): F3 (models, finishes first: F2 and F4 tests need its models), F1, F2, F4, F6. F2 and F4 begin with the code that needs no table and run their database-backed tests once the orchestrator has committed F3's six model tasks.
- **Stage A'** (when a slot frees; no dependency on stage A): F7. Inside stage A the agents never wait for each other's modules: F2 receives F1's redactor by injection (`load({ models, secretBox, redactor })`, lazy `require` as the default), and F4 resolves F7's `events`, `maintenanceMode` and `runtime` lazily or through injected fakes (`deps.bus`, `deps.maintenanceMode`, `bind`).

## Implementation strategy

### MVP first (W0 + US2 + US3)

Phase 1 → Phase 2 (W0) → Phase 3 acceptance → Phase 4 (US2) → Phase 5 (US3) → full-suite run. This is the first demonstrable increment: a secured panel (US1), a live dashboard with in-process restart (US2) and every setting editable, live and with encrypted secrets (US3). It already removes the need to edit `config.env` or read the console QR for most owners, and it carries the riskiest foundations (router and CSRF guard, settings accessor, secret box, logger redactor). Stop and validate there before widening the batch.

### Incremental delivery

1. W0: foundation and US1 → checkpoint.
2. Batch A: US2 and US3 (MVP), then US4 (pairing), US5 (command state), US6 (groups and group guard), with the P3 tails of W-DASH (US7) and W-SET (US12).
3. Batch B: US8 (data), US9 (broadcasts), US10 (backup), US11 (maintenance), US13 (alerts).
4. W2: merge, polish, ops, hardening, review.

Each story phase ends with a checkpoint that can be validated on its own with its tests and the matching quickstart §3 scenario.

### One branch, one PR

The user decided on a single branch (`002-admin-panel`) and a single PR. The orchestrator commits after each finished agent (French conventional commits: `feat(admin): …`, `test(admin): …`, `docs(admin): …`), so the history stays reviewable even though the PR is one.

### Cost control (user's rule)

- Every task runs on Sonnet 5.5; Opus is planned for nothing and is used only if a core W0 piece (F2, F5, F8) fails review twice.
- Agents receive their task IDs, the contract sections cited by the tasks and the rules above, not the whole spec, so each reads only what it needs.
- Never more than about five agents at once.
