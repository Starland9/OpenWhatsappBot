## Format: `- [ ] T### [P?] [USn?] Description — agent X (sonnet)`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task). An agent still runs its own tasks in ID order, so `[P]` mostly marks tasks of different agents of the same wave.
- **[USn]**: user story US1 to US4 from spec.md (omitted on pure infrastructure and on `main` tasks). One tag per task: the story it serves most directly; the coverage table at the end gives the full mapping.
- **Agent / model**: each task ends with `— agent X (sonnet)`. Per the user's routing rule every agent is `sonnet` (Sonnet 5.5 subagent); Opus is planned for nothing and is used only if a core W0 piece (T010, T011) fails review twice. `main` is the orchestrating session. Agent ids: A-ENG, B-DATA, C-UI (W0); D-BOT, E-API (W1); F-GRP, G-CMD (W2); Z-DOC (W3); R-REV (W3 review, read-only).
- Cites such as "per contracts/runtime.md §2.2" or "routes PERM-5 to PERM-7 of contracts/admin-permissions-api.md" name the exact contract section to read. Quoted text in a model task is verbatim from [data-model.md](data-model.md).

## Rules for every implementation agent (include in each agent prompt)

1. **Read first**: `CLAUDE.md`, the contract sections cited by your tasks ([contracts/runtime.md](contracts/runtime.md), [contracts/admin-permissions-api.md](contracts/admin-permissions-api.md), [contracts/panel-ui.md](contracts/panel-ui.md), [data-model.md](data-model.md)), and the decisions U1-U8 and X1-X12 in [research.md](research.md). For anything HTTP-visible the API contract wins; for engine and registry behaviour the runtime contract wins; for screens and panel texts `panel-ui.md` wins.
2. **Edit only the files listed in your tasks.** Never edit a file owned by another agent in the same wave; list the need under "Requests" in your final report. Never edit `lang/*.json`, `lib/admin/public/i18n/*.json` (generated by the merge tool, C-UI T022 only), `package.json`, `yarn.lock`, the design documents of `specs/003-command-permissions/` or any file marked "nobody" above. No new npm dependency.
3. **Never read or print** `config.env`, `sessions/`, `data/`, `database.db` or any secret. **Run every ad-hoc script, tool and test command with `OWB_NO_CONFIG_ENV=1`** (`config.js` then skips `config.env`; `test/helpers/fakes.js#setupEnv` sets it for tests). Tests use `DATABASE_URL=":memory:"`, `fs.mkdtemp` directories, fake numbers such as `237690000001`, fake clocks and stubs; nothing touches the real `data/`, `sessions/` or `database.db`, and nothing needs the network.
4. **No commits.** The orchestrator commits after each finished agent (French conventional commits on `003-command-permissions`, one per finished agent). Do not run `git stash`, `git reset`, `git checkout` or anything that rewrites the working tree of other agents.
5. **Runtime**: `export PATH=$HOME/.nvm/versions/node/v24.20.0/bin:$PATH` before any command. Yarn is vendored: `node .yarn/releases/yarn-4.17.0.cjs <command>`. Use the agent's scratchpad directory for temporary files, never the repository.
6. **Before finishing**: `node --check <file>` on every edited `.js` and `.mjs` file; run your own test files with `OWB_NO_CONFIG_ENV=1 node --test --test-force-exit test/<file>.test.js`; run the whole suite (`node .yarn/releases/yarn-4.17.0.cjs test`, with `BOT_LANG=fr` and `BOT_LANG=en` once). A failure in a file you do not own is reported as a Request, never fixed in place. **SC-004**: no existing test expectation changes except the lists in data-model §5 (B-DATA T013-T015, E-API T047-T048), the `TABS` expectation (F-GRP T035), the `summarizeDetail` additions (G-CMD T045) and the second fragment directory (C-UI T022). Any other existing test that fails is a regression in your code: stop and fix the code, never the expectation.
7. **Style**: match the surrounding code. CommonJS (`.js`) everywhere except `lib/admin/public/**` (native ES modules, `.mjs`); the existing quote style of each edited file (double quotes in new files); 2 spaces; comment density like the neighbours. Browser code: no `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`, no `eval`/`new Function`, no inline `<script>` or `style=`, no URL to a third-party host (strict CSP); only CSS classes that already exist in `app.css` (panel-ui.md §10 "CSP, CSS and accessibility" gives the list; there is no `badge-neutral` rule); no new CSS, icon, component or router entry; no DOM access at import time.

Tests are written first and seen to fail (red) before the implementation (rule of every story phase).
14. **Capture-site rule** (CLAUDE.md): never copy a `config.X` into a module-level constant; this feature adds no setting, so the engine reads none.
15. **Final report**: for each owned file the status, the tests added and their result (including the full-suite result), contract deviations with the reason, the i18n keys the agent used that are missing from the fragment, and the "Requests" for files owned by others. ## Implementation strategy

### MVP first (W0 + US1, then US2)

Phase 1 → Phase 2 (W0) → Phase 3 (US1: the delegated `.vv` and `.save`, the E-API group routes, the group tab) → full-suite run. This is the first demonstrable increment and the original need: `.vv` handed to a co-manager without reopening the privacy hole fixed in 001. US2 (Phase 4) then closes the menu and help for "these people only". Stop and validate there before widening: US1 and US2 are the two P1 stories and rest on the riskiest foundations (engine, registry order, cache, identity matching).

### Incremental delivery

1. W0: engine, registry, flags, table, backup list, shared panel pieces → checkpoint T023.
2. W1: D-BOT and E-API deliver US1 and US2 on the bot and API side, then US3 (everywhere routes) and US4 (PERM-1, GRP-3/GRP-6, contract guard).
3. W2: F-GRP and G-CMD deliver the group tab (US1, US4) and the Commands page (US3, US4) with the audit detail.
4. W3: documentation, final verification, review, hand-off.

Each story phase ends with a checkpoint that can be validated on its own with its tests and the matching quickstart §3 scenario.

### One branch, one PR

Single branch `003-command-permissions`, French conventional commits (`feat(permissions): …`, `test(permissions): …`, `docs: …`), one commit per finished agent by the orchestrator.

### Cost control (user's rule)

- Every task runs on Sonnet 5.5; Opus is planned for nothing and is used only if a core W0 piece (T010 engine, T011 registry order) fails review twice.
- Agents receive their task IDs, the contract sections cited by the tasks and the rules above, not the whole spec, so each reads only what it needs.
- Never more than three agents at once (W0 has three, W1 and W2 two).
