# Research B: messaging engine (feature 004, Phase 0)

Scope: format modules, Baileys content, outbox/queue/pacing, recipients and policy, never-a-command, receipts, reply capture, quoting, mentions, media lifecycle, engine tests. Bot side only (`lib/messaging/**` and the few files it touches); HTTP (stream A), tables/settings/backup/alerts (C) and the SPA (D) are other streams. `spec.md` clarifications are final. Evidence is `file:line` on branch `004-messaging-api` (4ea4b61) and in `node_modules/baileys` 7.0.0-rc14 (paths below are relative to `node_modules/baileys/lib/`). ## B1. Format module contract and registry

**Decision.** One file per format in `lib/messaging/formats/<name>.js`, loaded in sorted order by `lib/messaging/formatRegistry.js#load()` (memoized; `load({ dir })` for tests). The right is **derived**, never declared: `messages.send.<name>` (a declared copy would only drift). Shape:

```js
module.exports = {
  name: "image",                 // = file basename, /^[a-z][a-z0-9_]{1,23}$/
  order: 20,                     // docs / form / rights ordering (default 100)
  interactive: false,            // true => replies are captured (buttons, list, poll)
  fields: { caption: { type: "string", maxLength: 1024, trim: true } },   // request.js#validate rules, format-specific only
  media: { kinds: ["image"], maxBytes: 16 * MB, required: true },        // absent = no media; kinds map to sniffed mimes (B10)
  check(input, ctx) {},          // optional: cross-field / semantic errors -> { "buttons[1].id": { code, params? } } | null
  async prepare(ctx) {},         // optional, send time: conversion -> { path, mime, ext } (a NEW file in the staging dir)
  build(ctx) {},                 // required, sync, pure: -> { content, transport?, meta?, secret? }
  interpretReply(ctx) {},        // required iff interactive: raw event + stored meta -> { choices: [...] } | null
  doc: { summary: "Send an image", examples: [{ to: "237600000000", caption: "Hello" }] },   // OpenAPI text, English
  form: { hints: { caption: { widget: "text" } } },                      // optional overrides, see below
};
```

- **Common fields** are merged by the registry, not repeated in modules: `to` (string, required), `quote` (public id of an earlier message), and the transport-level `wait` / idempotency key owned by stream A. A format redefining one of them fails the load. `mentions` and `linkPreview` stay in `text.js` (FR-042/FR-043).
- `build(ctx)` gets `{ input, media, prepared, target: { jid, kind }, waId, mentions, lang, randomBytes }` and returns `{ content, transport, meta, secret }`: `content` is the Baileys content; `transport` is `"message"` (default, `sock.sendMessage(jid, content, options)`) or `"interactive"` (the button-helper relay path, B2); `meta` (ids and option hashes only, < 4 KB, JSON) is stored for reply capture; `secret` (poll `messageSecret`) is stored encrypted. The engine owns the send options (`messageId: waId`, `quoted`), never the module. `waId` is known at build time because the engine pre-generates it (B3), which is what lets button ids embed it (B7).
- Input is persisted as `payload.json` in the staging directory (B10), not rebuilt from Baileys content, so a restart rebuilds with a fresh `waId`/media.
- **Validation.** `validate()` (`lib/admin/http/request.js:200-233`) is flat: `type: "object"` only type-checks (`:188-190`) and `array.items` takes one rule, so contacts, buttons and list choices cannot be declared, and OpenAPI could not be generated from them. Recommendation: extract the pure core into `lib/utils/schema.js#check(input, schema) -> { value, fields }`, add two backward-compatible rules, `shape: { ...schema }` (recursive, strict: an unknown nested key is `unknown_field`) and `unique: true` (arrays of scalars), and make `request.js#validate` a thin wrapper that throws `AdminError`. The engine (not allowed to require `lib/admin/**`) and stream A then validate with the same code, and stream A walks the same rule tree for OpenAPI. Error paths use `a[0].b` keys in the existing `fields` map. `check()` remains an escape hatch for what a rule cannot say (phone parsing, lat/lon pairs, option hash collisions). Alternative: inject `validate` into the engine (`createMessaging({ validate })`), rejected because the rule extensions would then live in a file the engine cannot read.
- **Documentation.** `doc.summary`/`description` and per-field `doc` strings are English literals used only for the OpenAPI file (a developer artefact, not panel or bot text). `doc.examples` are validated and built in a unit test (B11), so shipped examples cannot rot.
- **Panel form descriptor** (`registry.describe(name)`, JSON, consumed by D): `{ name, right, interactive, order, fields: [{ name, widget, required, min, max, minLength, maxLength, enum, item? }], media: { kinds, maxBytes, allowUrl } | null, example }`. Widgets are **derived** from the schema (string -> `text`, `textarea` when `maxLength > 255`, int/number -> `number`, boolean -> `switch`, enum -> `select`, array of scalars -> `list`, array with `shape` -> `repeater`, media -> `file` + `url`); `form.hints[name]` overrides a widget (`textarea`, `rows`) and nothing else. Labels are **keys** by convention, `api.formats.<name>.title` and `api.formats.<name>.fields.<field>` in the panel catalogs (`panel-api.json` fragment family, HTTP never sends prose); a test fails on a registered format missing a key in either catalog (SC-009 allows catalog edits only).
- **Registry API**: `get(name)`, `list()`, `rights()` (-> `["messages.send.text", ...]`, what C stores and D lists), `schemaOf(name)` (common + format fields), `describe(name)`, `FormatRegistryError`.
- **What fails at boot** (`FormatRegistryError` naming the file; the outbox `start()` and the API start both call `load()`, and an engine that cannot start is already isolated by `boot.js:229-232`): basename != `name`; invalid `name`; `build` missing or not a function; `fields` not an object of known rule types or colliding with a common field; `interactive` without `interpretReply`; `media.kinds` outside `sniff.KINDS` or `maxBytes` not a positive int; `prepare`/`check` present but not functions; duplicate `name`. A format with a bad `doc.examples` is a test failure, not a boot failure.

**Rationale.** Mirrors the plugin registry (alias map, load order, fail loud on duplicates) and keeps FR-092: one new file plus catalog entries. Splitting `prepare` (async, conversion) from `build` (sync, pure) lets the pipeline fail a conversion as `media_conversion_failed` (FR-058) before the at-most-once claim (B3) and makes `build` unit-testable against real Baileys (B11). Deriving the right and the widgets removes the two places a module author could forget something.

**Alternatives.** A class hierarchy (`class ImageFormat extends BaseFormat`): rejected, the codebase uses plain exported objects everywhere. Letting `build` call `sock.sendMessage` itself: rejected, it would put pacing, `messageId`, quoting, timeouts and the "sending" mark in every module (violates FR-093's intent for the send side). Hand-written JSON Schema per format: rejected, double maintenance.

**Evidence.** `lib/admin/http/request.js:13-19,146-194,200-233`; `lib/plugins/registry.js:195-232` (hook order and load-order model); `lib/core/boot.js:222-233`; `plugins/buttons.js:297-303`.

**Files.** new `lib/messaging/formatRegistry.js`, `lib/messaging/common.js` (COMMON_FIELDS, limits, `MessagingError { code, params, fields }`), `lib/messaging/formats/*.js` (13), `lib/utils/schema.js`; edit `lib/admin/http/request.js` (wrapper only).

## B2. Baileys v7 content per format

Common mechanics (all verified in source). `sock.sendMessage(jid, content, options)` builds the message with `generateWAMessage(jid, content, { ..., messageId: generateMessageIDV2(...), ...options })` (`Socket/messages-send.js:1068-1088`): **`options.messageId` overrides the id** (spread after it, `:1086-1087`), `options.quoted` goes to `generateWAMessageFromContent` (`Utils/messages.js:559-586`). After `relayMessage` it emits an own-events upsert of type `append` (`:1135-1139`, `emitOwnEvents` default true, `Defaults/index.js:55`). A media source `{ url }` starting with `http://`/`https://` makes Baileys **download it itself** (`Utils/messages-media.js:261-262`); anything else is a local `createReadStream` (`:264`). The engine therefore only ever passes `{ url: <absolute staged path> }` (asserted with `safeFs.assertInside`, `lib/utils/safeFs.js:295`), never a caller string and never a Buffer of a 100 MB file.

## B3. Outbox, queue and the shared send gate

**Decision.** Engine `lib/messaging/outbox.js`, factory `createOutbox(options)` plus a process-wide default, same shape as `broadcaster.js`: `start(client)` / `stop()` / `isRunning()`, `tick(now?)` as the test hook, `enqueue(input, { now, limits })`, `waitFor(id, ms)`, `cancelByKey(keyId, reason)`, `cancelAll(reason)`, `recover({ now })`, `sweepOrphans({ now })`, `subscribe(fn)`, `reconfigure()`. Options: `clock`, `random`, `timers`, `gate`, `config`, `settingsStore`, `models`, `stageRoot` (default `data/api-outbox`), `sniff`, `keyGuard` (injected by `lib/api`: `async (message, now) -> { ok } | { ok: false, reason: "revoked" | "expired" }`; always ok for source `panel`).

**Message life** (a row per message; the DB is the queue). Transitions are conditional `UPDATE ... WHERE status = <from>`; a lost race changes 0 rows and is ignored (`broadcaster.js` contract, `:28-31`).

```
accept   write data/api-outbox/<id>/payload.json (+ media), then INSERT status=queued, acceptedAt, expiresAt = acceptedAt + API_QUEUE_TTL_MS (10 min)
tick     1 expire   UPDATE queued -> expired WHERE expiresAt <= now           (then remove the stage)
         2 gate     bot connected? not in maintenance mode? gate.ready(now)?  else return
         3 pick     oldest queued (acceptedAt, id), keyGuard ok, API enabled, chat not banned (B4)
         4 verify   unknown number -> onWhatsApp ; group -> groupMetadata (B4)      [may fail the message: nothing was sent]
         5 prepare  conversion (still `queued`: a crash here loses nothing, the message resumes)
         6 claim    waId = generateMessageIDV2(sock.user.id); sentIds.remember(waId);
                    UPDATE ... SET status='sending', sendingAt=now, waId=:waId WHERE id AND status='queued' AND expiresAt > now   (1 row or abort)
                    gate.reserve(now); const done = maintenanceMode.begin()
         7 send     withTimeout(() => format.send(sock, jid, built, { messageId: waId, quoted }), 30 s (90 s with media))
         8 settle   ok -> sent (sentAt); error -> classify() below; UPDATE ... WHERE status='sending'; remove the stage; done(); emit
```

- **At-most-once.** The mark `sending` (with the pre-generated `waId`) is written *before* `sendMessage` and is the point of no return. Pre-generating the id (`options.messageId`, B2) also means that a row stuck in `sending` knows the id WhatsApp saw. Boot: `recover()` turns every `sending` row into `unknown` (error `interrupted`) and removes its stage; a `queued` row resumes unless `expiresAt` passed. Nothing ever moves a row out of `sending|sent|unknown` toward a resend. Send errors: `classify(err)` of the broadcaster (`lib/utils/broadcaster.js:205-216`) returns `timeout` / `connection_closed` -> status `unknown` (`DELIVERED_UNSURE`, `:93`: the message may have left); anything else is a definitive pre-network failure (Boom 4xx from content generation, media upload refused) -> `failed` with `send_failed`. A settle UPDATE that throws is retried once; if it still fails the row stays `sending` and the next boot reports `unknown` (never a resend).
- **Shared send gate** `lib/utils/sendGate.js`: `createSendGate({ clock, random })` returns `{ ready(at, extraMs = 0), waitMs(at, extraMs), reserve(at), seed(ms), lastSendAt() }` plus a process-wide `module.exports.shared`. `ready`: `at - last >= max(MIN_SPACING_MS, extraMs) * (1 + jitter)` with `jitter = random() * 0.2` drawn once per `reserve`, the exact formula of `broadcaster.js:1098-1101,1120-1121`. `MIN_SPACING_MS` is `max(2000, config.API_MIN_SPACING_MS)` read at call time (FR-035, up only; the catalog rule is `rules.int(2000, 600000)`).
- **Exact broadcaster change** (smallest that makes the gap global and starves nobody): keep its own `lastSendAt`/`jitter` (its per-broadcast `spacingMs` up to 10 min must not be reset by API traffic, or a busy API would starve a 60 s broadcast), and add the global floor next to it: `deliverOne` gets `if (!gate.ready(at)) return;` right after the existing `if (at - lastSendAt < gap) return;` (`:1101`) and `gate.reserve(at);` right after `lastSendAt = at; jitter = null;` (`:1120-1121`); `ensureLastSendAt` ends with `gate.seed(lastSendAt)` (`:1035`); `createBroadcaster` takes `options.gate` and defaults to a **private** gate (`createSendGate({ clock, random })`) so the many fake-clock engines of `test/broadcaster.test.js` cannot see each other; only the process-wide instance is built with the shared one (`:1308`: `createBroadcaster({ gate: require("./sendGate").shared })`). The outbox does the mirror: `gate.ready(at)` before the claim, `gate.reserve(at)` at the claim, `gate.seed(max(sendingAt))` at start so a restart cannot burst.
- **One send per tick**, `TICK_INTERVAL_MS` 1000 (`broadcaster.js:88`), `busy` flag against overlap, plus `kick()` on enqueue (runs a tick at once when idle, so the first message does not wait for the next second). The loop only works when `pendingHint > 0` (in-memory counter seeded by `COUNT(status='queued')` at start and kept by enqueue/settle/cancel), so an idle API costs one empty timer callback per second and zero queries.
- **Timers, enable/disable, capture-site rule.** No timer at `require`; `start()` creates the `setInterval` (unref'd) **only if** `config.ADMIN_PANEL && config.API_ENABLED` and registers `settingsStore.onChange(["API_ENABLED", "ADMIN_PANEL"], reconfigure)`; `reconfigure()` starts or stops the timer, and on disable runs `cancelAll("api_disabled")` (FR-002). With the API disabled at boot, `start()` still runs the one-shot `recover()` + `cancelAll` (no timer) so rows from a previous run never linger. Every number (`API_MIN_SPACING_MS`, `API_QUEUE_TTL_MS`, `API_MAX_QUEUE`, per-key quotas) is read through `config.X` at call time, never stored in a constant or a default parameter. The queue-wide tick interval is a constant, so there is no settings-derived timer to rebuild (`test/capture-sites.test.js` gets one new case: change the setting, the next tick uses it).
- **Atomic admission** (`enqueue`): inside `mutex.withLock("api-outbox", ...)` (`lib/utils/mutex.js:27`; the in-memory SQLite has one connection and a count-then-insert is two statements) it counts the key's pending, last-60-s and last-24-h rows and the global pending, refuses with `{ code: "rate_limited" | "queue_full", params: { kind, retryAfterMs } }` (retry = when the oldest counted row leaves its window), else inserts. Recommended extra refusal: `estimatedWait = (pending + 1) * 2.2 s > TTL` -> `queue_full` with that delay (at 500 pending the spec's TTL of 10 min cannot be honoured: 500 x 2.2 s = 18 min; open point 4).
- **Wait for the result**: `waitFor(id, ms <= 30000)` returns `{ promise, cancel }` backed by an in-process `Map<id, Set<resolve>>`; `emit()` resolves it on `sent | failed | expired | cancelled | unknown` (not on `delivered`/`read`, which would hold the request); a per-waiter unref'd `setTimeout` resolves with the current row at the deadline; the HTTP layer calls `cancel()` on `req.close`; at most 200 waiters (more answer at once with the current status).
- **Cancellation**: `cancelByKey(keyId, reason)` (`key_revoked`, called by the C service in the same request as the revoke) and `cancelAll("api_disabled")`: under the lock, select the `queued` ids, `UPDATE ... SET status='cancelled' WHERE id IN (...) AND status='queued'`, remove their stages. A message already `sending` is not cancelled (it is past the claim). The claim's CAS makes the race with a concurrent cancel safe: the worker's UPDATE changes 0 rows and it drops the message. `keyGuard` is also asked at the claim for keys that expired by date without any revoke.
- **Disconnection**: `client.ready()` false (`lib/baileys/client.js:638-640`) -> the tick returns after the expiry sweep; messages wait and expire at 10 min. The socket is read at send time (`client.getSocket()`), never cached. `maintenanceMode.isActive()` -> the tick returns; `maintenanceMode.begin()` brackets claim-to-settle so a restore waits for the in-flight send (`lib/utils/maintenanceMode.js:3-14`).
- **Server rejection after the relay.** Baileys reports an async negative ack as `messages.update { status: 0 (ERROR), messageStubParameters: [code] }` (`Socket/messages-recv.js:1511-1565`). The outbox maps it to `sent|unknown -> failed` with `whatsapp_rejected` (the only non-monotone transition) and, on `463` (account restricted, `Utils/decode-wa-message.js:65`, text `:30`) opens a **breaker**: the tick refuses to claim for 15 min and `options.onRestricted(code)` lets C raise the owner alert. This is the one signal Baileys gives that the number is being throttled, and the spec's first risk is the ban (open point 2).
- **Engine wiring**: `boot.js` `ENGINES` gets `{ name: "outbox", id: "../messaging/outbox", start: (engine, client) => engine.start(client) }` right after `broadcaster` (`lib/core/boot.js:34`), `createAdmin` receives `outbox: engineModules.outbox` (as `broadcaster`, `:171`), and `test/boot.test.js` (fake engines `:98-107`, ids check `:549-570`) gets the new entry. `housekeeping.js` resolves it lazily like the broadcaster (`optionalRequire("./broadcaster")`, `:112`, `sweepMedia` `:255`) and calls `outbox.sweepOrphans({ now })` (B10); the 30-day row retention is C's rule.

**Rationale.** The broadcaster already proved this shape (CAS claims, `tick(now)`, injected clock, `max(sentAt)` seeding, no retry). Two-phase send (prepare before claim) keeps conversions retryable and the `unknown` window as small as the network call. Counting quotas from rows makes them survive a restart.

**Alternatives.** An in-memory queue with persisted-on-shutdown snapshots: rejected (crash loses accepted messages; FR-038). A single global gate object that also holds the broadcaster's per-broadcast spacing: rejected (starvation shown above). Retrying `unknown`: rejected by FR-038. Calling `sendQuickReplies` for interactive formats: rejected (hidden second send).

## B4. Recipients and policy

**Decision.** `lib/messaging/recipients.js`:

- `parseRecipient(input) -> { kind: "private", jid } | { kind: "group", jid } | { error }`. A string with `@g.us` is a group id (shape `^\d{5,25}(-\d+)?@g\.us$`); anything else is a number parsed with the **feature-003 rule**: strip spaces, `+`, `-`, `.`, `(`, `)`, drop a leading `00`, require 8-15 digits not starting with `0` -> `<digits>@s.whatsapp.net` (`lib/admin/services/permissions.js:63-79`, `parsePerson`). That function lives under `lib/admin/**`, which an engine must not require: move its number branch into `lib/utils/permissions.js` as `parsePhoneNumber(text) -> { pn } | { error: "invalid_phone" }` and have `parsePerson` call it (a one-line change in 003's file, covered by its tests). A LID or any other JID is refused (`recipient_invalid`): the API addresses numbers and groups only. A JID equal to the bot's own PN/LID (`getBotJids`, `lib/utils/permissions.js:83-86`) is refused as `recipient_not_allowed` (B5).
- `evaluatePolicy(policy, target) -> { ok } | { ok: false, code: "recipient_not_allowed" }`, policy `{ mode: "list"|"known"|"any", entries: [jid] }` (C stores it):
  - `any`: ok.
  - `list`: private -> `target.jid` equals an entry (PN compare); an entry that holds only a LID is compared through `sock.signalRepository.lidMapping.getLIDForPN` when a socket exists (2 s timeout), else it does not match (fail closed). group -> exact id.
  - `known`: private -> `KnownChat` with `jid = pn` **or `pnJid = pn`**; group -> `KnownChat` row `kind = 'group'`, `leftAt IS NULL`. The existing `knownChats.assertDestinations` matches by `jid` only (`lib/utils/knownChats.js:358-359`), so a person recorded under a LID (`record()` stores `message.jid`, `:97-131`) would be missed; add `knownChats.isKnown(jid)` (one indexed query, `pnJid` is indexed: `lib/database/models/KnownChat.js:54`).
- `isChatDisabled(target)`: the pipeline's cached set, `require("../core/pipeline").getBannedChats()` resolved lazily (`lib/core/pipeline.js:29-41`, invalidated by the ban commands), tested for the PN **and** for the `jid` of any `KnownChat` row whose `pnJid` is the PN (the ban command stores `message.jid`, which is the LID in LID-addressed chats; `knownChats.isSelectable` does the same double test, `:293-297`). `chat_disabled` (FR-041) at accept time **and again at the claim** (a ban after acceptance).
- Order at accept time (FR-032 is stream A's pipeline): key, right, **recipient parse + policy + chat_disabled (this module)**, quotas (`enqueue`), content.
- **Existence check (FR-040), send time, step 4 of the tick**: skipped for groups and for any target `isKnown`. Otherwise `sock.onWhatsApp(pn)` (`Socket/socket.js:222-246`): `[{ jid, exists }]`, `[]` when absent; `exists !== true` or empty -> `failed / not_on_whatsapp` and **no gate reservation** (nothing left); the returned `jid` is the destination when it is a `@s.whatsapp.net` jid (WhatsApp normalises some national formats). A thrown error or a timeout (10 s) is *retryable*: the row stays queued and the next tick tries again until expiry. At most one lookup per tick (1/s), results cached in memory (positive 24 h, negative 10 min, 1000 entries): bulk number probing is itself a ban signal.
- **Group that cannot be posted to**: `sock.groupMetadata(jid)` at the claim step under `withTimeout(10 s)` (`Message#getGroupMetadata` is per-message and not reusable). A definitive Boom 403/404 (`extractGroupMetadata` throws `Boom(text, { statusCode })`, `Socket/groups.js:277-281`) -> `failed / not_in_group`; `metadata.announce === true` (`:328`) and the bot not admin -> `failed / group_announce_only`; a timeout/connection error -> retry next tick. Bot admin test: export `findParticipant` and `isAdminParticipant` from `lib/classes/Message.js` (`:160-180`, two names added to `module.exports`) and use them with `getBotJids`. Communities' announcement group has `announce: true`, so it is covered.
- LID vs PN: private chats are always addressed by PN (Baileys maps to LID internally); replies come back as LID with `remoteJidAlt` PN (`lib/classes/Message.js:52-73`), which only matters for reply capture (B7).

**Rationale.** The same number rules as 003 (FR-030); checks that need a live socket happen at send time because the bot may be disconnected at accept time (edge case "bot déconnecté": requests are accepted).

**Alternatives.** `onWhatsApp` at accept time: rejected (needs a connection, adds latency to the 1-second text path of SC-010, and the spec makes it a status transition). Accepting LID recipients: rejected (nothing in the spec asks for it, and policy lists would need both forms).

**Evidence.** As cited.

## B5. Never a command (FR-039, SC-008)

**Findings (source-verified).** (1) Everything this socket sends is upserted as `append` (`Socket/messages-send.js:1135-1139`; the button helper does the same for private chats, `button-helper/helpers/buttons.js:900-909`). (2) `lib/baileys/client.js:366` re-emits only `notify` and `lib/core/pipeline.js:241` re-checks it, so the append never reaches `processMessage`. (3) The event buffer cannot turn it into `notify`: `messages.upsert` of different types are flushed separately (`Utils/event-buffer.js:108-125`); the only promotion is for the *same message key* upserted as `notify` too (`:395-420`), i.e. a server echo, which WhatsApp does not send to the sending device (companion devices of the same account receive it, this one does not). (4) No other path: `messages.update` goes to `antiDeleteHandler.handleMessageDelete`, which only reacts to revokes and whose cache never stores `fromMe` messages (`lib/utils/antiDeleteHandler.js:115-120`); `trackmessages`/`afk`/`knownchats` are `onMessage` hooks reached only through the pipeline; retries (`sendMessagesAgain`) do not upsert.

**Decision.** Defence in depth, because the guarantee is a security invariant and the one real hole is outside this process:

1. `lib/messaging/sentIds.js` (`remember(id)`, `has(id)`; Map with 15-min TTL and 2000 entries, pruned lazily, no timer). The outbox calls `remember(waId)` **before** `sendMessage` (the id is pre-generated, B3), so even an echo arriving before the call resolves is known.
2. `pipeline.js#handleMessage`, first lines after the maintenance check (`:106`): `if (msg.key.fromMe && sentIds.has(msg.key.id)) { logger.debug("API message echo ignored"); return; }`. Pipeline changes go in that file only; the guard also keeps API content out of the anti-delete cache and the stats.
3. Recipient == the bot's own number is refused (B4): a note-to-self is the only same-account chat where `fromMe` traffic of this device could come back.
4. Residual risk, documented not coded: two bot processes linked to the *same* WhatsApp number receive each other's `fromMe` messages as `notify` and treat them as owner messages (already true today for any message the owner types). An id marker recognisable across processes would fix it but fingerprints every message of every deployment; rejected. Not altering the text (zero-width prefix) is also required: callers may legitimately send `!cmd` to another bot in a group.

**Test that pins it** (`test/messaging-never-command.test.js`): (a) outbox sends `.eval 1+1` and `.restart`, assert `sock.sent[0].content.text` is verbatim and `registry.executeCommand` (spied) is never called; (b) feed `pipeline.processMessage` a `fromMe` echo with the recorded `waId` (as owner) -> no `executeCommand`, no reply; the same echo with an unknown id *does* reach the pipeline (proves the guard is the cause, not a side effect); (c) with `fakeBaileys.js`, emit `messages.upsert { type: "append" }` for an own `.eval` and assert the client emits no `messages` event; (d) recipient = bot number -> `recipient_not_allowed`.

**Evidence / Files.** As cited; `lib/core/pipeline.js`, new `lib/messaging/sentIds.js`.

## B6. Receipts (FR-070)

**Findings.** Private chats: `handleReceipt` emits `messages.update` with `{ key: { remoteJid, id, fromMe }, update: { status, messageTimestamp } }`, status from `getStatusFromReceiptType`: no type = `DELIVERY_ACK` (3), `read`/`read-self` = `READ` (4), `played` = `PLAYED` (5) (`Socket/messages-recv.js:1181-1203`, `Utils/generics.js:265-281`). Groups: only `message-receipt.update` per participant (`:1186-1196`), no `messages.update`. `lib/baileys/client.js:464-467` already re-emits **every** `messages.update` on the `WhatsAppClient`. So the **minimal client change is none**: the outbox subscribes with `client.on("messages.update", handler)` in `start(client)` (the EventEmitter outlives reconnections) and `off` in `stop()`. Group messages stop at `sent` (spec assumption) because the group receipts are simply not consumed.

**Decision.** `handler(updates)`: for each `{ key, update }` with `key.fromMe`, `typeof update.status === "number"`, a non-group `remoteJid`: map `3 -> delivered`, `4|5 -> read`, `0 -> failed(whatsapp_rejected)` (B3), ignore `1|2`. One conditional UPDATE per event, **no SELECT, no lock**, by the indexed unique `waId` (the remoteJid may be a LID; the id is the only key used):
`delivered`: `SET status='delivered', deliveredAt=:t WHERE waId=:id AND status IN ('sent','unknown')`;
`read`: `SET status='read', readAt=:t, deliveredAt=COALESCE(deliveredAt,:t) WHERE waId=:id AND status IN ('sent','delivered','unknown')`.
A statement that changes 0 rows is a non-API id (the bot's own replies also get receipts) and costs one indexed lookup. Timestamps: `update.messageTimestamp * 1000` when present, else `now`. `status` moves forward only, so a late `delivered` after `read` is ignored.

**Bonus (cheap, technical).** `unknown` is upgraded by a receipt: a crash after the server accepted the message leaves the pre-generated `waId` in the row, and a delivery receipt for that id proves the send. Evidence-based, never a resend. For private chats only; a group `unknown` stays `unknown`.

**Rationale.** Zero change in `client.js`, zero per-message memory, survives restarts (the lookup is the DB). A SELECT-then-UPDATE or an in-memory id map would need bounds and reload logic for receipts that can arrive days later (`read`).

**Alternatives.** Forwarding `message-receipt.update` to show group read counts: rejected by the spec (groups stop at `sent`). An in-memory `Map<waId, id>`: rejected, lossy after a restart.

**Evidence / Files.** As cited; `lib/messaging/outbox.js` (handler), index `ApiMessage.waId` unique (C; a unique index on a *new* table respects the additive-sync rule, and several NULLs are allowed before the claim).

## B7. Reply capture (FR-072, US6)

**Wire ids.** Buttons and list rows carry `api:reply:<waId>:<callerId>` (<= 97 chars, `callerId` has no colon, B2). Embedding `waId` (known at build time, B3) identifies the API message from the click alone: no dependence on `contextInfo.stanzaId` (**DEVICE**: whether a native-flow response always quotes its message). The convention `<plugin>:<action>[:<nonce>][:<arg>]` of CLAUDE.md is kept (`api` / `reply` / waId / id); no other plugin consumes an `api:` id (they test their own prefix: `plugins/tictactoe.js:250`, `plugins/buttonmenu.js:143-145`; the quiz/guess hooks need `ownsMessage` of a game message, `plugins/quiz.js:423-440`), and the API hook consumes `api:` ids first.

**Numbered answers beyond 1 hour.** The API does **not** record in `buttonRegistry` (TTL 1 h, 500 entries, `lib/utils/buttonRegistry.js:10-11`): API traffic would evict the bot's own entries and the 7-day window needs persistence anyway. The mapping lives in `ApiMessage.replyMeta` (ids in display order, B1 `meta`), found through the quoted id = `waId`.

**Hook location.** A hook-only plugin `plugins/apireplies.js` (like `groupguard.js`, `trackmessages.js`: no `command`), thin; the logic is `lib/messaging/replies.js`:

```js
module.exports = {
  hookPriority: { handleButtonReply: 5, onMessage: 6 },
  async handleButtonReply(message) {},   // clicks and quoted numbers -> true when it is an API reply
  async onMessage(message) {},           // poll votes (type pollUpdateMessage) -> true when it is an API poll
};
```

- `handleButtonReply` runs at pipeline step 5 (`lib/core/pipeline.js:147-170`), before `onMessage`. (a) body starts with `api:reply:` -> parse; **always return true** (consumed even when the API is off, the message unknown or older than 7 days: US6 scenario 4 and 5, nothing else may react), record only if `config.API_ENABLED`, the row exists, `now <= acceptedAt + 7 days` and the chat kind matches (group id equal; private: the sender forms `message.sender`/`senderLid`/`jid` are not verified against the stored PN because LID mapping may be missing, the unguessable `waId` is the proof). (b) bare number `^\d{1,3}$`, `message.quoted?.key?.fromMe` and `message.quoted.id`: `ApiMessage.findOne({ where: { waId } })` (indexed; only for quoted replies to the bot's own messages, so the lookup is rare), `ids[n-1]` -> same recording. Not an API message -> `false` (other hooks proceed). Priority 5 puts it ahead of the games' `handleButtonReply` hooks, which only claim their own messages anyway.
- `onMessage` (priority 6, between `knownchats` 5 and `role` 10; `test/hooks.test.js:476-490` checks the *relative* order of the listed files, so it still passes; add `apireplies.js` to its list): for `message.type === "pollUpdateMessage"` look up `pollCreationMessageKey.id` as `waId`; not ours -> `false`; ours -> decode and record -> `true` (a vote has no body, so nothing else would act on it anyway, but consuming it keeps it out of `trackmessages` counters).
- A reply hook must stay cheap and never throw: `pipeline.runHooks` isolates each hook (`:90-100`).

**Records.** `ApiMessageResponse` (C): `(messageId, voterKey)` unique for polls (last vote replaces), append-only rows for clicks, a unique `sourceId` (the reply message's own id, so a redelivery cannot double-count), `kind`, `choices` (JSON ids or option indexes, never labels), `author` (normalized PN, else LID), `at`. Cap 5000 responses per message.

**Poll votes: what Baileys v7 rc14 does not do.** The decryption block of `processMessage` is **commented out** (`Utils/process-message.js:576-625`), so no `pollUpdates` arrive in `messages.update`; the vote reaches the bot as a normal `pollUpdateMessage` upsert (type `notify`) whose `vote` is `{ encPayload, encIv }`. `decryptPollVote` is exported (`:146-159`) and `getAggregateVotesInPollMessage` needs the poll content (`Utils/messages.js:755-790`) which we do not keep. Our own decode, exercised in the spike (round trip OK with a self-built vote): `pollEncKey` = the stored 32-byte secret (B2), HMAC context = `pollMsgId` (our `waId`) + creator JID + voter JID + `"Poll Vote"`; a wrong JID form makes AES-GCM throw ("unable to authenticate data"). The JID forms WhatsApp used (PN vs LID, device suffix) cannot be known offline, so the decoder **tries candidates**: creator in `{jidNormalizedUser(me.id), jidNormalizedUser(me.lid)}` (LID first when the chat is LID-addressed), voter in `{participant, participantAlt, remoteJid, remoteJidAlt}` normalized, at most 8 attempts, first success wins; none -> debug log + counter, no record, never an error. **DEVICE**: confirm which pair works on a PN chat and a LID group.

**Votes map to options without option text.** A vote carries `selectedOptions`: SHA-256 digests of the UTF-8 option names (`Utils/messages.js:761`; spike matched `sha256(Buffer.from(name))`). At build time the poll module computes the digests and returns them in `meta` (`{ hashes: [hex x N], multi }`, <= 12 x 64 chars), the row stores them with the encrypted secret (`secretBox.encrypt(hex, "api-poll:" + id)`, `lib/utils/secretBox.js`, AAD-bound), and `interpretReply` maps digests to indexes. No label is stored; the digests are not the text, but a short common option ("Yes") is guessable from its hash, a privacy trade-off worth one line to the owner (open point 5). Per voter `choices` is the full current selection (an empty array when the vote is cleared); the aggregate "total per option" is computed on read by counting current selections. A lost `panel.key` makes new votes undecodable (secret unreadable): recorded as nothing, never an error to the caller.

**Evidence.** As cited; `lib/classes/Message.js:80-108,245-284`; `lib/core/pipeline.js:147-170,173`; `lib/plugins/registry.js:212-232`; `test/hooks.test.js:476-490`.

## B8. Quoting an API message (FR-042) without storing content

**Findings.** `generateWAMessageFromContent` needs `quoted.key` and `quoted.message`; without `message` it throws a TypeError (spike). It copies the quoted content (minus its `contextInfo`) into `contextInfo.quotedMessage`, sets `stanzaId = quoted.key.id` and `participant` (the bot's own JID for `fromMe`) (`Utils/messages.js:559-586`). With `message: { conversation: "" }` the spike produced `{ stanzaId, participant, quotedMessage: { conversation: "" } }`. Whether the recipient's client then draws the original (found by `stanzaId`) or the embedded empty preview cannot be established offline (**DEVICE**).

**Decision.** `quote` is a public message id of the **same key** (source `panel` quotes panel messages) and the **same resolved chat**; the row must still exist (30-day history) and have a `waId`; otherwise `quote_not_found` (never reveals another key's message). The engine passes `options.quoted = { key: { remoteJid: row.chatJid, fromMe: true, id: row.waId }, message: shellFor(row.format) }`, where `shellFor` is a **typed empty shell derived from the stored `format` only**: `{ conversation: "" }` for text/location/contact/poll/buttons/list, `{ imageMessage: {} }` for image/sticker, `{ videoMessage: {} }` for video/gif, `{ audioMessage: {} }` for audio/voice, `{ documentMessage: {} }` for document. Nothing about the content is kept (FR-073), the quote links to the right message, and a client that renders the embedded preview shows a bare bubble of the right type. If the device check shows a blank bubble is unacceptable, the fallback is a **volatile** cache of the first ~100 characters of text messages, memory only, 1 h, never logged, lost on restart: that would contradict "jamais le texte" in the strict reading, hence open point 1.

**Rationale.** `stanzaId`-only is what the protocol needs to thread the reply; the preview is cosmetic. Fully respects FR-073 and survives restarts (needs only metadata already stored).

**Alternatives.** Persisting a text preview: rejected (FR-073). The in-memory preview cache: kept as a documented fallback only. Quoting a received message: out of scope (spec assumption).

**Evidence / Files.** `Utils/messages.js:559-586`; `lib/messaging/outbox.js` (`quotedFor(row)`), no other file.

## B9. Mentions by number in groups

**Decision.** `text.mentions` is an array (<= 50) of numbers parsed with the same rule as recipients; allowed only when the recipient is a group (`not_allowed` on a private chat). The text refers to a person as `@<number>`. At build time, from `groupMetadata` (already fetched in the claim step): a participant matches a mention when `normalizeJid(p.phoneNumber) === pn` or `normalizeJid(p.id) === pn` (`Socket/groups.js:335-343`: in PN groups `id` is the PN and `lid` is set; in LID groups `id` is the LID and `phoneNumber` the PN). The mention JID is `p.id` (the group's own addressing form); when it is a LID, the `@<number>` tokens of that person in the text are rewritten to `@<lid user part>` so the client's token-to-JID match works. Numbers that are not members are ignored (text left untouched, message still sent). Baileys then writes `contextInfo.mentionedJid` (`Utils/messages.js:494-513`, spike: `["237690000001@s.whatsapp.net"]`). The rewrite for LID groups and the rendered name are **DEVICE** checks.

**Alternatives.** Failing the message on a non-member: rejected (a leave between accept and send would turn a good text into a failure). Always sending the PN: risks a plain `@number` in LID groups.

**Files.** `lib/messaging/formats/text.js`, `lib/messaging/recipients.js` (`mentionJids(metadata, numbers)`).

## B10. Media lifecycle

**Decision.** Stage = `data/api-outbox/<publicId>/` (mode 0700, under the gitignored `data/`), holding `payload.json`, `media` (as received or downloaded and verified) and, after `prepare`, `prepared.<ext>`. Stream A streams the upload or the URL download straight into `media` with a byte cap through `outbox.openStage(id) -> { dir, mediaPath }`, then `messaging.inspectMedia(format, mediaPath) -> { kind, mime, ext, size }` runs `lib/messaging/sniff.js`:

- `sniff.classify(file, { name })` wraps `file-type` (`import("file-type")`, as `broadcaster.defaultSniff`, `:167-197`, which stays the source for `image`/`document`). Observed (v22.2, spike): jpeg/png/webp/gif as `image/*`; mp4 `video/mp4`, mov `video/quicktime`, a browser-style audio webm `video/webm`; mp3 `audio/mpeg`, opus `audio/ogg; codecs=opus`, m4a `audio/x-m4a`, wav `audio/wav`, flac `audio/flac`, aac `audio/aac`, amr `audio/amr`. `sniff.KINDS` maps format-declared kinds to allow-lists: `image` (jpeg, png, webp), `animated` (gif), `video` (mp4, quicktime, 3gpp), `audio` (the audio list), `audio_or_container` (audio + `video/webm` + mp4, for `voice` only, ffmpeg extracts the track), `document` (the broadcast whitelist, `broadcaster.js:96-106`). Mismatch -> `media_type_mismatch` with `{ expected, detected }` and the file is deleted at once (US2.4).
- Size: the cap is `min(format.media.maxBytes, MAX_UPLOAD MB)` at call time; stream A stops reading at the cap (`media_too_large`).

**Deletion.** The terminal UPDATE (`sent|failed|expired|cancelled|unknown`) is committed first, then `fs.rm(dir, { recursive, force })` through `safeFs.assertInside(stageRoot, dir)` (`broadcaster.js:554-563` pattern). A crash between the two leaves an orphan, never a lost state. `recover()` removes the stage of every row it moves to `unknown`.

**Orphan sweep.** `outbox.sweepOrphans({ now })` (daily, from `housekeeping.js`, and once at `start()`): any stage directory older than 1 h (grace for an accept in progress) whose row is missing or not in `queued`/`sending` is removed; a `queued` row whose directory vanished is failed as `payload_unavailable` at its next pick (never a text-only send: the `media_unavailable` rule of `broadcaster.js:1042`). It reports `{ removed, freedBytes }`. Content never touches the database: `payload.json` lives with the media, so an exported backup (stream C lists `ApiMessage` rows only) cannot contain text; the stage directory must be listed as excluded from backups (C).

**Conversion failure.** `prepare` throws (ffmpeg non-zero, sharp error, `null` sticker) -> `failed / media_conversion_failed` while the row is still `queued` (nothing sent, B3 step 5), stage removed. ffmpeg missing (`err.code === "ENOENT"`, `lib/utils/ffmpeg.js:79`) -> `failed / media_conversion_failed` too, and one warn log.

**Evidence / Files.** `lib/utils/ffmpeg.js:27-107`; `lib/utils/safeFs.js:295`; `lib/utils/housekeeping.js:32,255`; new `lib/messaging/sniff.js`.

## Interfaces with other streams

**To A (HTTP).** Facade `lib/messaging/index.js`: `formats` (registry), `validateInput(formatName, body) -> input` (throws `MessagingError("validation_failed", { fields })`), `resolveRecipient(to, policy) -> target` (throws `recipient_invalid | recipient_not_allowed | chat_disabled`), `openStage(id)`, `inspectMedia(formatName, file)` (`media_type_mismatch`), `enqueue(...)`, `waitFor`, `getMessage`. Error codes the engine can produce at accept time: `validation_failed`, `recipient_invalid`, `recipient_not_allowed`, `chat_disabled`, `rate_limited` (`params.kind`, `retryAfterMs`), `queue_full`, `media_type_mismatch`, `media_too_large`, `quote_not_found`; at send time (status `failed` + `errorCode`): `not_on_whatsapp`, `chat_disabled`, `not_in_group`, `group_announce_only`, `media_conversion_failed`, `payload_unavailable`, `whatsapp_rejected`, `send_failed`; `cancelled` reasons `key_revoked | api_disabled`; `unknown` reason `interrupted | timeout | connection_closed`. A needs the shared-schema extraction (`lib/utils/schema.js`, rules `shape`/`unique`) and walks `registry.schemaOf/describe/doc` for OpenAPI. `Idempotency-Key` and `wait` stay in A; the outbox returns the existing row for a replay when A passes `existingId`.

**To C (data/panel/ops).** `ApiMessage` columns the engine needs: public `id`, `keyId` (null = panel), `source`, `idempotencyKey`, `chatJid`, `format`, `size`, `status`, `errorCode`, `acceptedAt`, `expiresAt`, `sendingAt`, `sentAt`, `deliveredAt`, `readAt`, `finishedAt`, `waId` (**unique**, nullable), `replyMeta` (TEXT JSON, ids/hashes only), `pollSecret` (TEXT, `enc:v1:`), indexes `(status, acceptedAt)`, `(keyId, acceptedAt)`, `waId`. `ApiMessageResponse` as in B7 with unique `(messageId, voterKey)` for polls and unique `sourceId`. Settings read by the engine: `API_ENABLED`, `API_MIN_SPACING_MS` (int >= 2000), `API_QUEUE_TTL_MS` (default 600000), `API_MAX_QUEUE` (500), `API_REPLY_WINDOW_DAYS` (7), per-key quotas passed in `limits`. Wiring: `ENGINES` entry, `outbox` into `createAdmin`, `housekeeping` calls `outbox.sweepOrphans` and the 30-day purge, `cancelByKey` in the revoke service, `onRestricted(code)` -> an alert, the stage directory excluded from backups, the new tables in `lib/admin/backup/format.js` `MODELS`/`EXCLUDED_MODELS`.

**To D (panel UI).** `registry.describe(name)` JSON (B1), `registry.rights()`, the i18n key convention `api.formats.<name>.title` / `.fields.<field>` and the widget set (`text textarea number switch select list repeater file url`); the test form posts to the same facade with source `panel` (no key, no key quotas, queue caps apply).

## Open points for the owner

1. **Quote preview of an API message.** Recommended: typed empty shell + `stanzaId` (nothing of the content is kept, B8); the recipient may see a bare quote bubble. Alternative: a volatile in-memory preview of the first ~100 characters (1 h, lost at restart), which strains "jamais le texte". Decide after the phone check.
2. **Auto-pause on a WhatsApp restriction.** Recommended: when WhatsApp answers `463` (account restricted) the API queue pauses 15 minutes and the owners are alerted; queued messages keep their expiry. The alternative is to keep sending, which risks a harder ban.
3. **Numbered text inside button/list messages.** The spec says the numbered version MUST be in the message; phones that show native buttons then also show the numbers. Recommended: keep it (spec), accept the redundancy.
4. **Admission by estimated wait.** At 2-2.4 s per message, the spec's 500 pending cannot all leave within the 10-minute expiry (about 270 can). Recommended: refuse early with `queue_full` and the delay when `(pending + 1) x 2.2 s` exceeds the expiry, rather than accept messages that will certainly expire.
5. **Poll option digests kept for 7 days** (needed to turn votes into option numbers; the text is not kept, but a very common option is guessable from its digest). Recommended: accept; the alternative is to return raw digests to callers, which is unusable.
6. **Document types.** Recommended: the broadcast whitelist (PDF, Office/OpenDocument, zip, txt, csv), so the API cannot be used to push executables; confirm no other type (json, xml, apk) is wanted.
