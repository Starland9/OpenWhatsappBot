## Format: `- [ ] T### [P?] [USn?] Description — agent X (sonnet)`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task). An agent still runs its own tasks in ID order, so `[P]` mostly marks tasks of different agents of the same wave.
- **[USn]**: user story US1 to US7 from spec.md (omitted on `main` tasks and on pure cross-cutting work). One tag per task: the story it serves most directly; the coverage table at the end gives the full FR and SC mapping.
- **Agent / model**: each task ends with `— agent X (sonnet)`. Per the user's routing rule every agent is `sonnet` (Sonnet 5.5 subagent); Opus is planned for nothing and is used only if a security-critical piece (the API pipeline order T041, the key store T039, the URL fetcher T081, the outbox at-most-once T060, the step-up widening T116) fails review twice. `main` is the orchestrating session (`— main`). Agent ids: A-UTIL, B-DATA (W0); C-FMT, D-HTTP (W1); E-OUT, G-STEP (W2); F-PUB, H-PANEL (W3); I-UI, J-DOC (W4); R-REV (W5 review, read-only).
- Cites such as "per contracts/runtime.md §4.3" name the exact contract section to read. Quoted text in a model task is verbatim from [data-model.md](data-model.md). A task that says "write first" produces tests that fail before the implementation task of the same agent.
- A ticked checkbox (`- [X]`) is implemented and committed on `004-messaging-api`.

## Rules for every implementation agent (include in each agent prompt)

1. **Read first**: `CLAUDE.md`, the contract sections cited by your tasks ([contracts/public-api.md](contracts/public-api.md), [contracts/runtime.md](contracts/runtime.md), [contracts/admin-api.md](contracts/admin-api.md), [contracts/panel-ui.md](contracts/panel-ui.md), [data-model.md](data-model.md)) and the decisions U1-U15, X1-X22, Y1-Y17 of [research.md](research.md). Where `research/*.md` disagrees with `research.md` or a contract, the latter wins. For anything on the wire (bodies, errors, headers, step order) `public-api.md` wins; for engine, queue, modules and boot `runtime.md` wins; for panel routes, shapes and codes `admin-api.md`; for screens, panel texts and render guards `panel-ui.md`; for columns, indexes and the status machine `data-model.md`.
2. **Edit only the files listed in your tasks** (and the ownership table). Never edit a file owned by another agent in the same wave; list the need under "Requests" in your final report. Never edit `package.json`, `yarn.lock`, the design documents of `specs/004-messaging-api/` or any file marked "nobody". **No new npm dependency** (the multipart parser is hand-written, `link-preview-js` is never added). Catalogs are edited only through the fragments and the merge tools by the owner of the wave; never by hand.
3. **Never read or print** `config.env`, `sessions/`, `data/`, `database.db` or any secret. **Run every ad-hoc script, tool and test command with `OWB_NO_CONFIG_ENV=1`**. Tests use `DATABASE_URL=":memory:"`, `fs.mkdtemp` data roots, fake numbers such as `237690000001`, fake clocks and injected resolvers; nothing touches the real `data/`, `sessions/` or `database.db`, and nothing needs the network or a phone.
4. **No commits.** The orchestrator commits after each finished agent or session (French conventional commits on `004-messaging-api`). Do not run `git stash`, `git reset`, `git checkout` or anything that rewrites the working tree of other agents.
5. **Runtime**: `export PATH=$HOME/.nvm/versions/node/v24.20.0/bin:$PATH` before any command. Yarn is vendored: `node .yarn/releases/yarn-4.17.0.cjs <command>`. Use the agent's scratchpad directory for temporary files, never the repository.
6. **Resource limits (standing rule, an out-of-memory test once closed the editor)**: an agent runs **only single test files**, always with the cap and the timeout: `OWB_NO_CONFIG_ENV=1 timeout 120 node --max-old-space-size=1024 --test --test-force-exit --test-timeout=30000 test/<file>.test.js`. Agents **never** run the full suite and never two test processes at once. `main` runs the full suite once per checkpoint, fr then en, never two suites at once: `OWB_NO_CONFIG_ENV=1 NODE_OPTIONS=--max-old-space-size=1024 timeout 600 node .yarn/releases/yarn-4.17.0.cjs test` (and the same with `BOT_LANG=en`). On exit 137 or "heap out of memory": stop, bisect with a smaller cap, report; do not retry blindly. View tests use `createDom` of `test/helpers/fakeDom.js` with the render guards of contracts/panel-ui.md §9 (`test/helpers/viewGuard.js`: scripted `fetch`, `guard.assertClean()` in a `finally` that also unmounts, `dom.settle(n)` with a small fixed `n`, `after()` restoring the guard, the DOM and `globalThis.fetch`).
7. **Before finishing**: `node --check <file>` on every edited `.js` and `.mjs` file; run your own test files (rule 6). A failure in a file you do not own is reported as a Request, never fixed in place. **No existing test expectation changes except these**, each by the owner named in the ownership table: settings 101 to 112 entries (78 editable, 34 read-only, 22 secrets, 5 restart; env-less entries accepted by `settings-example`); backup `EXCLUDED_MODELS` 7 to 11 and `seedExcluded` (`MODELS` stays 26); the created-tables lists of `database.test.js` (+4 tables); `AlertOutbox.TYPES` and the alert type lists 6 to 9 (`database`, `alerts`, `admin-alerts`, `admin-view-alerts`); hook rows for `apireplies.js` (`onMessage` 6, `handleButtonReply` 5) and a plugin count +1 where a test pins it; `boot.test.js` (the `messaging` engine between `broadcaster` and `alerts`, `apiState` collaborator, `options.deps`); `pipeline.test.js` and `capture-sites.test.js` (additions); `housekeeping.test.js` (five report keys); `panel-legacy.test.js` (`/api/v1/*` rows) and `admin-logging.test.js` (walkers); `admin-http.test.js` (`stepUp` in the `routes()` row keys); `admin-i18n.test.js` (`FRAGMENT_DIRS`, `EXTRA_SERVER_CODES`, `AREAS`, dynamic families, 112 settings); `admin-integration.test.js` (`SECTIONS` third entry), `admin-security.test.js` (the `stepUp` set, the four tables in the GET-writes-nothing dump), `admin-audit.test.js` (ten actions), `admin-uploads.test.js` (purpose `api`); `admin-frontend.test.js` (`AREAS`, `CONFIRMED_ACTIONS` 14 to 18, the second scan route list), `admin-view-logs-stats.test.js` (`api` prefix, `summarizeDetail` branches); `admin-memory.test.js` (`MODES` `api-off`, `api-on`); additions to `permissions.test.js`, `knownchats.test.js`, `helpers.test.js`. Any other existing test that fails is a regression in your code: stop and fix the code, never the expectation (SC-009 spirit: a new format or endpoint edits no existing file).
8. **Style**: match the surrounding code. CommonJS (`.js`) everywhere except `lib/admin/public/**` (native ES modules, `.mjs`); double quotes in new files; 2 spaces; comment density like the neighbours. Browser code: no `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`, no `eval`/`new Function`, no inline `<script>` or `style=`, no `console.*`, no URL to another host in a module or a catalog text (strict CSP, `test/admin-frontend.test.js`); only CSS classes that already exist in `app.css` (the list of contracts/panel-ui.md §10; the only new rule is `.code-block`); no DOM access at import time; no `setInterval` and `setTimeout` only in `api-watch.mjs`.
9. **i18n**: every bot text goes through `getLang("<key>", ...args)`, never `getLang(k) || "fallback"`; `en` and `fr` carry the same keys; a literal text passed to `reply()` or `sendMessage` fails `test/i18n.test.js` (`// i18n-ignore` only for a deliberate exception). The HTTP API sends codes and parameters, never prose; the OpenAPI document and `Catalog.endpoints[].summary` are English only (U8). French texts: vouvoiement, "panel d'administration", never "panneau"; a panel text never contains a URL.
10. **Secrets and logs (RT-05, Y9, SC-003)**: never log, audit, return or store beyond the contracts the key token, its secret or its `lookupId`, a message text, caption, file name, URL, option or button label, or a recipient in clear (a log uses `mask(jid)`, a message `publicId` or `waId`, a key its integer `id` and `name`); use `safeLog(err)` from `lib/utils/http.js` (never log an axios error); no `console.*` in `lib/admin/**`, `lib/api/**`, `lib/messaging/**` (use `createLogger` from `lib/utils/logger.js`); no `pino(` anywhere. Serialisation is by explicit field lists (data-model.md §9), never `row.get()` or `toJSON()`. JSON columns are read through model instances, never `raw: true` (data-model.md §0.2).
11. **Layering and lifecycle (RT-01 to RT-08)**: `lib/messaging/**` and `lib/utils/{sendGate,schema,apiState}.js` never require `lib/api/**` or `lib/admin/**` (single exception: `apiState.setPlainHttpFrom` lazily requires the leaf `lib/api/ipRules.js`); `lib/api/**` requires from the panel only `lib/admin/http/*`, `lib/admin/auth/rateLimit.js` and `lib/admin/logs/redactor.js`; panel routes and services resolve engines lazily (`deps.x || require(...)` inside `register()` or the handler) so a test can inject a fake. No timer, listener, socket, directory or query at `require`; heavy modules (`sharp`, `node-webpmux`, `file-type`, ffmpeg, `urlFetch`, `stickerMaker`, `plugins/buttons.js`) are required inside the function that needs them (SC-011); every `config.X` is read at call time, never in a module-level constant, a class field or a default parameter, and a value copied into a row (`expiresAt`, `repliesUntil`) is a snapshot; every function that depends on time takes `now` or an injected clock; multi-statement writes run under `mutex.withLock`, every other write is one conditional `UPDATE ... WHERE status = :from` and a lost race (0 rows) is ignored.
12. **Routes**: every public endpoint declares a right (registry build fails otherwise; there is no public endpoint); every panel route declares `auth: "session"` plus `csrf` and `stepUp` where the contract says; validation is a strict schema that builds a fresh object (an unknown property is `422 validation_failed` with `$unknown`); a handler returns codes and parameters of the error envelope, never prose, in the stage order of its route; panel audit goes through `ctx.audit(...)` once per request and only when something changed, with the closed detail sets of admin-api.md §1.7.
13. **Panel views**: each file that calls the panel declares `const base = "/admin/api/api";` once at the top and builds every call from it (contract test 11 of `test/admin-frontend.test.js`); `useAsync`/`useEffect`/`useMemo`/`useCallback` have explicit dependency arrays of primitives; a draft is never re-synchronised by an effect (remount with a `key`); polling is a `setTimeout` chain with a counter and a cap; `api-logic.mjs` and `api-form-logic.mjs` stay pure (no DOM, no network, no timer, no `t()`; a function that needs a text returns a panel key plus params).
14. **Tests**: style of the neighbours (`test/helpers/fakes.js` `setupEnv`, `fakeSocket`, `makeMessage`; `fakeClock.js`; `adminHarness.js` with `adminClient.js`; `fakeDom.js`; `fakeBaileys.js`). New helper files go in `test/helpers/` and belong to the agent that creates them; `fakes.js` is edited only by A-UTIL (T015). Tests are written first and seen to fail (red) before the implementation of their story; no test needs a phone, the network or the real ffmpeg (a test that needs ffmpeg skips itself when it is absent).
15. **Final report**: for each owned file the status, the tests added and their single-file results, contract deviations with the reason, the panel or bot keys the agent used that are missing from a fragment, and the "Requests" for files owned by others. The orchestrator feeds the Requests into the next wave.

## Implementation strategy

### MVP first (W0, W1 core, then US1)

Phase 1 → Phase 2 (W0, then the W1 cores) → Phase 3 (US1: the text format, the engine, PUB-1, the enable and key screens) → the W3 checkpoint (T147) is the first moment the MVP can be validated end to end with the harness and a sandbox run of [quickstart.md §3.1-3.4](quickstart.md). US2 (Phase 4) follows in the same waves and closes the second P1 story; stop and validate at T147 before the panel UI of W4. US1 and US2 rest on the riskiest pieces (the pipeline order, the key store, the URL fetcher, the outbox at-most-once), which is why they get the review of T154.

### Incremental delivery

1. W0: shared utilities, tables, state, IP grammar, settings, backup exclusion, first texts → T029.
2. W1: format registry, recipients, media inspection, SSRF fetcher, the whole HTTP core of the API against fakes → T145.
3. W2: the engine (queue, pacing, receipts, retention, replies, alerts, boot) and the step-up backend with the pure panel logic → T146.
4. W3: the four public endpoints with the contract, security, availability and leak suites, and the panel routes API-1 to API-13 → T147 (US1 to US7 backend complete).
5. W4: the panel API area and the documentation → T151, then W5 verification, review and hand-off.

Each story phase ends with a checkpoint that can be validated on its own with its tests and the matching quickstart scenario.

### One branch, one PR

Single branch `004-messaging-api`, French conventional commits (`feat(api): …`, `feat(messaging): …`, `feat(admin): …`, `test(api): …`, `docs: …`), one commit per finished agent or session by the orchestrator, all with the attribution line of the session.

### Cost control (user's rule)

- Every task runs on Sonnet 5.5; Opus is planned for nothing and is used only if a security-critical piece (T041, T039, T081, T060, T116) fails review twice.
- Never more than two implementation agents at once (every wave has exactly two), plus the optional read-only reviewer alone in W5.
- Agents receive their task IDs, the contract sections cited by the tasks and the rules above, not the whole spec, so each reads only what it needs.
- Memory discipline (standing rule): single test files with `--max-old-space-size=1024`, `timeout 120` and `--test-timeout=30000`; the full suite only by `main`, once per checkpoint, fr then en, never two suites at once; on exit 137 or "heap out of memory" stop and bisect.

## Notes

- `[P]` = different files and no dependency on an incomplete task. An agent still runs its own tasks in ID order.
- Agents never commit; the orchestrator commits after each finished agent (or session) and files the "Requests" of the final reports into the next wave (panel and bot keys go into the fragments by the owner of the wave, merged with the tools, dry run first).
- **Large agents run in sessions.** C-FMT, D-HTTP, E-OUT and I-UI have 15 to 24 tasks. `main` may split a wave agent into two sessions of the same agent id along a phase boundary (for example E-OUT: Phase 3 then Phases 4 to 8; I-UI: Phases 3 and 5 then Phases 6 and 9), committing between the sessions, and relaunch the same agent id with the remaining task IDs. The file ownership and the two-agents-at-once limit do not change; a session never starts while two agents are alive.
- If a task needs a change in a file owned by another agent of the same wave, the agent reports a Request; `main` batches the Requests at each checkpoint (T029, T145, T146, T147, T151).
